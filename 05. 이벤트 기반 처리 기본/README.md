# 05. 이벤트 기반 처리 기본

이벤트 기반 마이크로서비스는 최소 세 단계로 동작한다. 입력 이벤트 스트림에서 이벤트를 소비하고, 이벤트를 처리하고, 필요한 출력 이벤트를 생산한다. 5장은 이 흐름 중 상태를 가지지 않는 처리(stateless processing)의 기초를 다룬다. 토폴로지 구성, 변환과 스트림 분기, 리파티션과 코파티션, 컨슈머 인스턴스에 파티션을 할당하는 전략, 인스턴스 실패 복구가 주제다.

## 5.1 상태 비저장 토폴로지 구성

마이크로서비스 토폴로지는 이벤트에 적용하는 일련의 작업이다. 컨슈머가 이벤트를 받아 반응하는 구조이므로 사고 방식을 이벤트 주도로 바꿔야 한다. 필터, 라우터, 변환, 구체화, 취합 같은 기능을 조합한다.

### 5.1.1 변환

변환(transform)은 이벤트 하나를 처리해 하나 이상의 출력 이벤트를 내는 과정이다. 주요 종류는 다음과 같다.

- 필터(filter): 기준을 충족하면 이벤트를 통과시킨다. 0개 이상의 이벤트를 낸다.
- 맵(map): 이벤트 키, 값, 또는 둘 다를 변경해 정확히 1개의 이벤트를 낸다. 키를 바꾸면 데이터 지역성을 유지하기 위해 리파티션이 필요할 수 있다.
- 맵밸류(mapValue): 키는 그대로 두고 값만 바꿔 정확히 1개의 이벤트를 낸다. 리파티션이 필요 없다.
- 맞춤 변환(custom transform): 맞춤 로직으로 상태를 조회하거나 다른 시스템과 동기 통신을 한다.

### 5.1.2 스트림 분기 및 병합

분기는 이벤트의 속성(국가, 표준 시간대, 출처, 제품 등)에 따라 다른 출력 스트림으로 보내는 작업이다. 처리 오류가 발생한 이벤트를 데드 레터 큐(dead letter queue)로 보내는 패턴도 분기다.

병합은 여러 입력 스트림을 하나로 합치는 작업이지만 실제로 의미 있는 시나리오는 드물다. 마이크로서비스는 보통 필요한 만큼 여러 입력 스트림을 그대로 소비해 비즈니스 로직을 수행한다. 굳이 병합한다면 병합된 도메인을 나타내는 새로운 통합 스키마를 정의해야 하며, 그런 도메인이 의미 없다면 전체 설계를 다시 봐야 한다.

## 5.2 이벤트 스트림 리파티션

이벤트 스트림은 이벤트 키와 파티셔너(partitioner) 로직으로 파티셔닝된다. 일반적으로 해시 함수로 키를 특정 파티션에 확정적으로 매핑하므로 같은 키의 이벤트는 같은 파티션으로 들어간다. 리파티션은 다음 중 하나 이상을 바꿔 새 스트림을 생산하는 행위다.

- 파티션 수: 다운스트림 병렬도를 높이거나 코파티션을 위해 다른 스트림과 파티션 수를 맞춘다.
- 이벤트 키: 같은 키의 이벤트가 같은 파티션에 모이도록 키를 변경한다.
- 이벤트 파티셔너: 파티션 선택 로직을 변경한다.

병렬도 증가 외의 목적으로 상태 저장 처리기가 직접 리파티션하는 일은 드물다. 보통 상태 비저장 마이크로서비스가 다운스트림 상태 저장 처리기를 위해 이벤트를 미리 리파티션해준다.

같은 키를 가진 모든 이벤트를 한 파티션에 모으면 데이터 지역성이 확보된다. 컨슈머는 한 파티션만 소비해도 그 키의 전체 그림을 얻을 수 있고, 컨슈머를 여러 인스턴스로 확장해 파티션 단위로 나눠 처리할 수 있다. 리파티션과 데이터 지역성은 대규모 상태 저장 처리의 필수 요소다.

## 5.3 이벤트 스트림 코파티션

코파티션(co-partition)은 두 이벤트 스트림이 파티션 수와 파티셔너 로직을 동일하게 맞추도록 하는 것이다. 한 스트림의 키 있는 이벤트를 다른 스트림의 같은 키 이벤트와 같은 노드에 배치하기 위해 필요하다. 스트리밍 조인 같은 다중 상태 저장 작업에서는 출처가 어느 스트림이든 같은 키의 이벤트가 같은 노드에서 처리되어야 하므로 코파티션이 필수다.

## 5.4 컨슈머 인스턴스에 파티션 할당

마이크로서비스는 고유한 컨슈머 그룹을 유지해 입력 스트림의 오프셋을 집합적으로 관리한다. 컨슈머 인스턴스가 그룹에 등록되면 이벤트 브로커가 파티션을 할당한다.

파티션 할당 방식은 브로커마다 다르다. 카프카는 컨슈머 그룹의 첫 등록 클라이언트(컨슈머 그룹 리더)가 파티션 어사이너 역할을 맡는다. 펄사는 브로커 내부에서 중앙 집중식으로 관리한다.

파티션을 재할당할 때는 모든 작업을 잠시 멈춰 경합 조건과 중복 출력을 막는다.

### 5.4.1 파티션 어사이너로 파티션 배정

대량 데이터 처리를 위해 컨슈머 인스턴스를 여러 개 띄우면 파티션 어사이너(partition assigner)가 공평하고 안정된 방식으로 파티션을 분배한다. 인스턴스 추가나 삭제 시 재할당도 어사이너가 담당한다. 어사이너 컴포넌트는 브로커 종류에 따라 컨슈머 클라이언트에 탑재되거나 브로커 내부에서 관리된다.

### 5.4.2 코파티션된 파티션 할당

코파티션으로 표시된 모든 파티션은 같은 컨슈머 인스턴스에 함께 할당되어야 한다. 그래야 인스턴스가 해당 비즈니스 로직 수행에 필요한 이벤트 데이터의 하위 집합을 정확히 받는다. 여러 스트림의 파티션 수가 일치하지 않으면 어사이너 코드에서 오류를 던지는 것이 좋다.

### 5.4.3 파티션 할당 전략

목표는 두 가지다. 인스턴스의 처리 능력이 동등하다는 전제 아래 파티션을 고루 분배하는 것, 그리고 리밸런스 시 재할당되는 파티션 수를 최소화하는 것. 후자가 중요한 이유는 샤딩된 구체화 상태를 다룰 때 재할당으로 엉뚱한 샤드를 가리키게 되는 비용 때문이다.

세 가지 기본 전략은 다음과 같다.

- 라운드 로빈 할당: 전체 파티션 리스트를 인스턴스에 차례로 분배. 코파티션된 스트림은 별도 리스트로 묶어 함께 할당한다.
- 정적 할당: 특정 파티션을 특정 컨슈머에게 고정 할당. 내부 상태 저장소에서 대용량 상태를 구체화할 때 유용하다. 인스턴스가 그룹을 떠나도 일정 시간 동안 재할당하지 않고 복귀를 기다린다.
- 맞춤 할당: 외부 신호나 도구로 클라이언트 요건에 맞춘 로직을 직접 작성. 입력 스트림의 현재 컨슈머 랙 상태에 따라 작업 부하를 균등 분산하는 방식이 한 예다.

## 5.5 상태 비저장 처리 인스턴스 실패 복구

상태 비저장 처리 실패 복구는 컨슈머 그룹에 새 인스턴스를 추가하는 것과 같다. 복구할 상태가 없으므로 파티션을 할당받고 오프셋을 확보하는 즉시 곧바로 이벤트 처리를 시작한다.

## 5.6 마치며

상태 비저장 이벤트 기반 마이크로서비스는 이벤트를 소비하고 처리하고 후속 이벤트를 낸다. 각 이벤트는 다른 이벤트와 독립적으로 처리된다. 키와 파티셔너 알고리즘, 파티션 수가 동일한 두 스트림을 코파티션됐다고 한다. 코파티션은 데이터 지역성을 확보해 상태 저장 처리의 토대가 되며, 파티션 어사이너는 인스턴스 간 균등 분배와 코파티션 정합을 함께 책임진다. 이 개념들은 7장의 상태 저장 처리에서 다시 등장하며, 그에 앞서 6장에서는 여러 파티션과 스트림에 걸친 이벤트 순서 처리(비순차 이벤트, 지각 이벤트)를 다룬다.
