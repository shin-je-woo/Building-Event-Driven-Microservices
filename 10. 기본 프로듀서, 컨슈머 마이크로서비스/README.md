# 10. 기본 프로듀서/컨슈머 마이크로서비스

기본 프로듀서/컨슈머(Basic Producer and Consumer, BPC) 마이크로서비스는 이벤트 브로커가 제공하는 단순한 프로듀서/컨슈머 클라이언트만 사용해 이벤트를 발행하고 소비한다. 가벼운 컨슈머/프로듀서 클라이언트를 쓰는 기본 구현체이며, 풀스택 스트림 처리 프레임워크와 달리 추가 인지 오버헤드 없이 시작할 수 있다. 다만 적용 상황을 잘 골라야 한다. 10장은 BPC의 알맞은 용도와 외부 스트리밍 처리와의 하이브리드 패턴을 다룬다.

## 10.1 BPC의 알맞은 용도는?

BPC는 가벼운 컨슈머/프로듀서 클라이언트만 의존하므로 새 비즈니스 요건을 빠르게 구현할 수 있고, 풀스택 프레임워크의 사용 제약에서 자유롭다. 그러나 마이크로서비스 토폴로지를 직접 관리해야 하고 모든 동기화와 일관성 보장도 코드로 책임져야 한다. 다음 네 가지 상황에 BPC가 적합하다.

### 10.1.1 기존 레거시 시스템과 통합

이벤트 기반 아키텍처로 옮기는 과도기에 적합하다. 다른 이벤트 기반 마이크로서비스와 통합해야 하지만 동기식 요청-응답 인터페이스(주로 API 호출)에 묶여 있는 레거시 시스템이라면, 기존 코드를 그대로 두고 BPC 패턴으로 이벤트 인터페이스만 덧붙이는 편이 적은 비용으로 가장 큰 가치를 만든다.

### 10.1.2 이벤트 순서와 무관한 상태 저장 비즈니스 로직

이벤트 순서가 비즈니스 로직에 영향을 주지 않는 경우에 적합하다. 예제로 책 평점 집계가 있다. 동일 도서(ISBN 키)에 대한 평점 이벤트는 어느 순서로 처리되든 최종 집계 결과가 같아야 한다. BPC는 외부 데이터 저장소를 사용해 평점을 누적하고, 이벤트가 도착할 때마다 단순히 더해 나간다. 처리 순서가 다르더라도 결과는 동일하다.

### 10.1.3 데이터 레이어가 너무 많은 일을 하는 경우

BPC는 쿼리, 트랜잭션, 인덱싱, 캐시 등 풀스택 프레임워크가 직접 다루기 어려운 데이터 레이어 기능을 활용해야 할 때 유리하다. 일반 RDB의 트랜잭션과 쿼리 능력을 그대로 쓰면서 이벤트 기반으로 상태를 유지할 수 있다. 데이터 양이 매우 크고 빈도가 높은 경우, 풀스택 프레임워크의 내장 상태 저장소 대신 외부 저장소의 분산 처리 능력을 그대로 활용할 수 있다.

### 10.1.4 독립적으로 처리 및 데이터 레이어 확장

처리 레이어와 데이터 레이어를 독립적으로 확장해야 할 때 BPC가 적합하다. 풀스택 프레임워크는 두 레이어가 결합되어 한쪽만 확장하기 어렵지만, BPC는 외부 데이터 저장소가 처리 인스턴스와 분리되어 있어 자유롭게 늘리고 줄일 수 있다. 데이터 양이 큰 분석 작업이나 다수 사용자의 동시 R/W가 일어나는 시스템에 알맞다.

## 10.2 하이브리드 BPC 애플리케이션으로 외부 스트리밍을 처리

BPC는 외부 스트림 처리 프레임워크와 결합해 강점을 살릴 수 있다. 풀스택 프레임워크가 가진 윈도잉, 워터마크, 비순차 처리, 상태 관리 같은 기능을 활용하면서 BPC의 유연한 데이터 레이어와 통합 능력은 그대로 유지한다.

### 10.2.1 예제: 외부 스트림 처리 프레임워크를 이용해 이벤트 스트림 조인

조인 같은 복잡한 연산이 필요할 때 BPC가 직접 구현하는 대신 외부 스트림 처리 프레임워크(아파치 스파크, 플링크, KSQL 등)를 호출한다. BPC는 입력 이벤트를 가공해 프레임워크에 넘기고, 프레임워크가 조인을 처리한 뒤 결과 스트림을 BPC가 다시 소비해 비즈니스 로직을 적용한다.

## 10.3 마치며

BPC는 단순한 프로듀서/컨슈머 클라이언트만으로 마이크로서비스를 구축하는 가장 가벼운 방식이다. 풀스택 프레임워크의 제약 없이 빠르게 적용할 수 있어 레거시 시스템과의 통합, 이벤트 순서와 무관한 상태 저장 비즈니스 로직, 외부 데이터 레이어의 활용, 처리와 데이터 레이어의 독립 확장이 필요한 경우에 적합하다. 외부 스트림 처리 프레임워크와 하이브리드로 결합하면 윈도잉이나 조인 같은 복잡한 처리도 BPC의 유연성을 잃지 않고 수행할 수 있다.
