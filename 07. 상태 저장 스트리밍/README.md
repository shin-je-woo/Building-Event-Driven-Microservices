# 07. 상태 저장 스트리밍

대부분의 마이크로서비스는 상태를 유지해야 한다. 상태 저장 스트리밍은 이벤트 기반 마이크로서비스의 중요한 근간이다. 7장은 상태를 어디에(내부/외부 상태 저장소) 어떻게 구체화하고, 체인지로그로 어떻게 복구하며, 재구성과 마이그레이션 중 무엇을 선택하고, 실제로 한 번 처리(effectively once)를 어떻게 보장하는지 다룬다.

## 7.1 상태 저장소와 이벤트 스트림에서 상태 구체화

두 용어를 구분해야 한다.

- 구체화 상태(materialized state): 소스 이벤트 스트림의 이벤트를 투영해 만든 불변의 사본. 마이크로서비스가 공통 비즈니스 엔티티로 사용한다.
- 상태 저장소(state store): 서비스가 비즈니스 상태와 중간 계산 결과를 저장하는 가변 저장소.

상태를 두는 곳은 크게 두 가지다. 처리기와 같은 컨테이너 안의 내부 저장소, 또는 컨테이너 밖의 외부 스토리지 서비스.

## 7.2 체인지로그 이벤트 스트림에 상태 기록

체인지로그(changelog)는 상태 저장소의 모든 변경 사항을 기록한 이벤트 스트림이다. 테이블-스트림 이원성에서 테이블 변경을 다시 스트림으로 변환한 결과다. 이벤트 브로커에 저장되어 마이크로서비스 외부에 영구 사본으로 유지되며, 상태 재구성과 체크포인트 수단으로 쓰인다.

체인지로그는 최근 키-값 쌍만 있어도 상태 재구성이 가능하므로 컴팩션해야 한다. 카프카 스트림즈는 체인지로그를 기본 제공하지만 기본 프로듀서/컨슈머 클라이언트는 지원하지 않으므로 직접 구현이 필요하다.

## 7.3 내부 상태 저장소에 상태 구체화

내부 상태 저장소는 마이크로서비스 비즈니스 로직과 같은 컨테이너에 있다. 각 인스턴스는 자신에게 할당된 파티션의 이벤트만 구체화하고 파티션별로 데이터를 논리적으로 분리한다. 리밸런스로 회수된 파티션의 상태는 그냥 삭제하면 되고, 다시 할당될 때는 입력 스트림이나 체인지로그에서 재구성한다.

RocksDB 같은 고성능 키-값 저장소가 주로 쓰이며 로컬 SSD에 최적화되어 메모리 초과 데이터 세트도 빠르게 처리한다.

### 7.3.1 전역 상태 구체화

전역 상태 저장소(global state store)는 모든 파티션 데이터를 각 인스턴스에 전체 사본으로 보관한다. 자주 조회되지만 거의 바뀌지 않는 소규모 데이터 세트(공통 검색 테이블, 디멘전 테이블)에 적합하다. 인스턴스마다 전체 사본을 가지므로 출력 중복과 비확정적 결과가 발생할 수 있어 이벤트 기반 로직의 동인으로는 쓰지 않는다.

### 7.3.2 내부 상태의 장점

- 확장이 단순하다. 이벤트 브로커와 컴퓨팅 클러스터가 확장을 떠맡아 인스턴스 수만 늘리고 줄이면 된다.
- 고성능 디스크 활용. 로컬 SSD의 RocksDB는 랜덤 액세스 읽기 지연이 65 마이크로초 수준이다. 인메모리만큼은 아니지만 NAS보다 훨씬 빠르다.
- NAS 사용 가능. 처리량은 떨어지지만 상태가 볼륨에 유지되어 하드웨어 교체가 쉽고 체인지로그 재구성 없이 중단 지점부터 재개할 수 있다.

### 7.3.3 내부 상태의 단점

- 런타임에 정의된 디스크에 묶인다. 볼륨을 늘리려면 서비스를 멈춰야 하고, 대부분의 CMS는 볼륨 축소를 지원하지 않는다.
- 디스크 공간 낭비. 트래픽 피크에 맞춘 디스크를 항상 확보해야 해서 외부 종량 과금 서비스보다 비효율적일 수 있다.

### 7.3.4 내부 상태의 확장과 복구

새 인스턴스 추가와 실패 복구는 같은 프로세스다. 새 이벤트 처리 전에 정의된 모든 상태를 구체화해야 하며 가장 빠른 방법은 체인지로그에서 다시 로드하는 것이다.

핫 레플리카(hot replica)는 파티션별로 추가 복제본을 다른 인스턴스에 유지해 무중단 운영을 가능하게 한다. 카프카 스트림즈에 내장되어 있다. 인스턴스가 죽으면 파티션 어사이너가 핫 레플리카가 있는 인스턴스를 우선 선택해 즉시 처리를 재개한다. 트레이드오프는 디스크 사용량 증가다.

복구 경로는 두 가지다. 체인지로그가 있으면 거기서 재로드한다(이 시간 동안 새 이벤트를 처리하면 비확정적 결과가 나오므로 처리하면 안 된다). 체인지로그가 없으면 입력 스트림 맨 처음부터 모든 이벤트를 다시 소비해야 한다. 후자는 시간이 훨씬 오래 걸리며 재처리 중 생산된 이벤트가 다운스트림에 중복으로 보일 수 있으므로 멱등하거나 중복 제거 가능한 경우에만 적합하다.

## 7.4 외부 상태 저장소에 상태 구체화

외부 상태 저장소는 마이크로서비스 컨테이너 밖에 있지만 보통 같은 로컬 네트워크 안에 둔다. 관계형 DB, 문서형 DB, BLOB, 검색 시스템, 고가용성 분산 키-값 저장소가 흔히 쓰인다.

공통 데이터 스토리지 플랫폼에 둘 수는 있어도 마이크로서비스 간에 데이터 세트를 공유해서는 안 된다. 다른 마이크로서비스의 상태에 직접 접근하면 강결합이 생기므로, 각 마이크로서비스는 자신의 상태 사본을 반드시 따로 구체화해야 한다.

### 7.4.1 외부 상태 저장소의 장점

- 완전한 데이터 지역성. 각 인스턴스가 모든 구체화 데이터에 접근할 수 있어 다중 요소 검색, 외래 키 조인, 지리공간 쿼리에 파티션 지역성이 필요 없다. 일관성 보장을 위해 강한 쓰기 후 읽기 기능이 있는 저장소를 쓴다.
- 익숙한 기술. 조직이 이미 운영 중인 데이터 저장소를 그대로 활용해 프로덕션 배포 노력을 줄일 수 있다. FaaS나 기본 프로듀서/컨슈머 패턴에서 특히 유리하다.

### 7.4.2 외부 상태의 단점

- 여러 기술을 관리해야 한다. 비즈니스 로직과 별개로 외부 저장소를 직접 관리, 확장, 모니터링해야 한다. 책임을 다른 팀에 전가하면 기술적 상호 의존이 발생하므로 절대 금물이다.
- 네트워크 지연으로 인한 성능 저하. 캐싱과 병렬화로 완화할 수 있지만 복잡도와 비용이 늘고 모든 워크로드가 병렬화 가능한 것도 아니다.
- 비용. 트랜잭션 수, 페이로드 크기, 보존 기간 단위로 과금되고 부하 급증 대비 오버 프로비저닝이 필요하다.
- 완전한 데이터 지역성의 역설. 여러 인스턴스가 같은 외부 데이터를 공유하면 어느 인스턴스가 공유 상태에 어떻게 기여했는지 추적과 디버깅이 어렵다. 각 인스턴스의 스트림 시간은 독립적이므로 경합 조건과 비확정적 동작도 늘어난다.

### 7.4.3 외부 상태 저장소의 확장과 복구

마이크로서비스 측은 인증 정보만 새 인스턴스에 추가하면 되어 간단하지만, 하부 상태 저장소의 확장과 복구는 사용 기술에 종속되어 복잡하다. 상태 구성 전략은 세 가지로 일반화된다.

- 소스 스트림 사용: 모든 입력 스트림의 컨슈머 오프셋을 초기 시점으로 되돌려 새 사본을 만든다. 중단 시간이 가장 길고 사실상 애플리케이션 전체 리셋이라 모든 출력 이벤트가 재생성된다.
- 체인지로그 사용: 내부 상태 저장소와 동일한 방식으로 외부 저장소도 체인지로그에서 다시 채울 수 있다.
- 스냅샷 사용: 외부 저장소가 제공하는 백업/복구 기능을 활용한다. 저장된 상태가 멱등적이면 컨슈머 오프셋을 스냅샷 시점 직전 값으로 잡아 적어도 한 번 이상 처리를 보장한다. 멱등적이지 않으면 오프셋을 데이터 안에 함께 저장해야 일관성이 유지된다.

소스 스트림이나 체인지로그에서 외부 저장소를 재구성하는 작업은 네트워크 지연 때문에 매우 오래 걸린다. 마이크로서비스 SLA에 영향을 주지 않는지 확인해야 한다.

## 7.5 재구성과 상태 저장소 마이그레이션

비즈니스 요건 변경으로 상태 저장소 구조를 바꿔야 할 때 두 방법이 있다.

### 7.5.1 재구성

마이크로서비스를 멈추고 입력 스트림 오프셋을 초기 시점으로 리셋한 뒤 중간 상태를 삭제한다. 새 버전을 시동해 입력 스트림을 다시 읽어 상태를 재구성한다. 새 비즈니스 로직에 따른 새 출력 이벤트가 모두 생성되며, 이는 중복이 아니라 변경 사항이 다운스트림에 전파되는 것이다.

상태 재구성은 시간이 오래 걸릴 수 있어 SLA 영향을 점검해야 한다. 가장 큰 장점은 재해 복구 절차를 일상적으로 검증하게 된다는 점이다. 입력 이벤트에만 존재하는 필드를 추출해야 하는 비즈니스 요건이라면 재구성이 유일한 방법이다.

### 7.5.2 마이그레이션

거대한 상태 저장소는 재구성 비용이 너무 클 수 있다. 예를 들어 출력 이벤트에 옵션 필드 하나만 추가하는 변경이라면 옛 데이터를 재처리할 필요가 없다. 관계형 DB라면 기본값이 NULL인 컬럼을 추가하고 애플리케이션을 재배포하면 된다.

비즈니스 니즈와 데이터 변경이 복잡할수록 마이그레이션 리스크가 커진다. DB 마이그레이션은 비즈니스 로직 밖에서 일어나므로 재구성 시에는 없을 비정합성이 스며들 수 있다. 마이그레이션을 택하면 실무에 가까운 데이터로 철저히 검증하고 재구성 결과와 비교해야 한다.

## 7.6 트랜잭션과 실제로 한 번 처리

실제로 한 번 처리(effectively once)는 프로듀서, 컨슈머, 브로커 실패와 상관없이 단일 진실 공급원에 모든 업데이트가 일관되게 적용되도록 보장한다. 같은 데이터가 여러 번 처리되더라도 결과가 한 번 처리한 것과 같다는 의미여서 정확히 한 번보다 정확한 표현이다.

멱등적 쓰기(idempotent writes)는 카프카, 펄사 같은 브로커가 널리 지원하며, 쓰기 도중 실패하더라도 재시도로 중복 이벤트가 생기지 않게 한다.

브로커가 트랜잭션을 지원하면 가장 강력하다. 카프카는 완전한 트랜잭션을 지원해 여러 이벤트를 여러 스트림에 원자적으로 쓸 수 있다. 트랜잭션 미지원 브로커에서는 클라이언트 측에서 직접 구현해야 한다.

### 7.6.1 예제: 재고 회계 서비스

제품별 입출 이벤트를 받아 현재 재고를 계산하고 임곗값 미달 시 알림을 발행하는 서비스다. 각 이벤트가 정확히 한 번 적용되지 않으면 계산이 틀어지므로 실제로 한 번 처리가 필요한 전형적 사례다.

### 7.6.2 클라이언트-브로커 트랜잭션으로 실제로 한 번 처리

출력 이벤트 생산, 체인지로그를 통한 내부 상태 업데이트, 컨슈머 오프셋 증가를 모두 단일 원자 트랜잭션으로 묶는다. 세 업데이트가 모두 브로커의 이벤트 스트림 안에 저장될 때만 가능하다. 트랜잭션 도중 프로듀서가 실패하면 브로커는 미커밋 트랜잭션을 보지 않고, 컨슈머는 오프셋 순서를 따르므로 트랜잭션이 완료될 때까지 블로킹 후 재개한다. 일시적 오류는 단순 재시도로 해결된다.

프로듀서가 치명적 예외를 만나면 다른 인스턴스로 교체하고 체인지로그에서 복구하며, 컨슈머 오프셋도 오프셋 스트림에 저장된 마지막 정상 위치로 리셋된다.

### 7.6.3 클라이언트-브로커 트랜잭션 없이 실제로 한 번 처리

브로커가 트랜잭션을 지원하지 않으면 더 많은 작업이 필요하다. 사후 중복 제거에 의존하기보다 멱등적 쓰기를 지원하는 브로커를 쓰는 편이 낫다.

중복 이벤트가 생기는 두 시나리오는 다음과 같다.

- 프로듀서가 ACK를 받지 못해 재시도하는 경우. 같은 데이터지만 새 오프셋을 가진 이벤트가 생성된다.
- 프로듀서가 발행 후 컨슈머 오프셋 업데이트 전에 실패하는 경우. 재가동 시 같은 작업을 반복해 새 사본이 만들어진다.

중복 식별은 dedupe ID(중복 제거 ID)로 한다. 키, 값, 생성 시간 등 카디널리티가 높은 속성으로 해시를 만들어 같은 이벤트는 같은 해시값을 갖도록 한다. 은행 계좌 이체, 전자상거래 주문, 배송 차감 같은 케이스가 적합하다. 키 없는 이벤트는 파티션 지역성이 보장되지 않아 중복 방지가 매우 어렵다.

중복 방지는 dedupe ID 색인을 컨슈머 측에서 관리하고 받은 이벤트를 비교해 거르는 식으로 한다. 모든 이벤트를 무기한 보관하는 것은 시간과 공간 비용이 막대하므로 실제로는 TTL, 최대 캐시 크기, 주기적 삭제 잡으로 작게 유지한다. 파티션 간 중복 제거는 비싸므로 단일 파티션 안에서만 수행한다.

상태 저장소의 트랜잭션 기능을 이용해 실제로 한 번 처리를 구현할 수도 있다. 컨슈머 오프셋 관리를 브로커에서 외부 데이터 서비스로 옮겨, 상태 변경과 오프셋 업데이트를 단일 트랜잭션으로 묶는다. 트랜잭션 실패 시 마지막 정상 상태로 되돌리고 데이터 서비스가 복구될 때까지 소비를 중단한다. 단, 이는 실제로 한 번 처리이지 실제로 한 번 생산이 아니다. 비트랜잭션 클라이언트-브로커 구조에서는 중복 이벤트 생산이 불가피하므로 출력은 적어도 한 번 이상 생산이 보장된다.

상태 저장소를 업데이트하면서 동시에 이벤트를 트랜잭셔널하게 생산해야 하면 4장의 아웃박스(변경 데이터 테이블) 패턴을 활용한다. 출력 스트림에 적어도 한 번 이상 생산하면서 상태 저장소는 실제로 한 번 업데이트되어 최종 일관성이 보장된다.

## 7.7 마치며

내부 상태 저장소는 고성능 처리에 강하고 외부 상태 저장소는 비즈니스 요건에 맞춘 유연한 옵션을 제공한다. 체인지로그는 백업과 복구의 중요한 수단이며 트랜잭션 DB나 스냅샷도 대안이 된다. 트랜잭션을 지원하는 이벤트 브로커는 강력한 실제로 한 번 처리 메커니즘을 제공해 컨슈머의 중복 방지 책임을 덜어준다. 트랜잭션 미지원 시스템에서는 dedupe 기반 중복 제거로 같은 보장을 달성할 수 있다.
