# 04. 기존 시스템에 이벤트 기반 아키텍처 통합

이벤트 기반 아키텍처로 전환하려면 레거시 시스템에 갇혀 있는 도메인 데이터를 이벤트 스트림으로 꺼내야 한다. 이것이 데이터 해방(data liberation)이다. 4장은 데이터 해방의 세 가지 패턴(쿼리 기반, CDC 로그 기반, 아웃박스 테이블 기반)과 각각의 트레이드오프, 그리고 반대 방향인 이벤트 싱킹과 조직 문화 측면의 시사점을 다룬다.

## 4.1 데이터 해방이란?

데이터 해방은 교차 도메인 데이터 세트(cross-domain data sets)를 식별해 각각의 이벤트 스트림에 발행하는 마이그레이션 전략이다. 기존 서비스와 데이터 저장소 간의 점대점 의존을 분석하면 어떤 데이터를 해방시켜야 하는지 드러난다. 해방된 이벤트 스트림은 단일 진실 공급원이 되며 시스템은 더 이상 원본 데이터 저장소에 직접 결합하지 않는다.

### 4.1.1 데이터 해방 시 고려 사항

해방된 스트림과 원본 데이터 세트는 최종 일관성(eventual consistency) 수준에서 동기화된다. 이상적으로는 모든 상태를 이벤트 스트림 단일 진실 공급원에서 생성하고 복구할 수 있어야 하지만 모든 애플리케이션을 그렇게까지 리팩터링하는 것은 실용적이지 않다. 레거시 시스템은 다음과 같은 제약 때문에 리팩터링이 어렵다.

- 개발자 지원 제약. 적은 공수로 해방할 솔루션이 필요하다.
- 리팩터링 비용. 동기식 MVC를 비동기 이벤트 기반과 혼합하려면 비용이 크다.
- 레거시 지원 리스크. 식별되지 않은 점대점 의존 때문에 변경이 예기치 않은 결과를 부른다.

타협안은 단방향 이벤트 기반 아키텍처다. 레거시 시스템은 이벤트를 읽지 않고 데이터만 외부 스트림으로 흘려보낸다.

### 4.1.2 해방된 데이터를 이벤트로 변환

해방된 이벤트도 3장의 스키마화 권장 사항을 따른다. 명시적 스키마와 호환성 보장이 필수이며, 조직 전체적으로 통용되는 동일한 표준 포맷을 적용한다. 우선순위는 비즈니스 전반에서 가장 자주 사용되는 데이터에 둔다.

## 4.2 데이터 해방 패턴

하부 데이터 저장소에서 데이터를 추출하는 패턴은 세 가지다.

- 쿼리 기반(query-based): 데이터 저장소를 쿼리해 결과를 추출. 어떤 저장소에도 가능.
- 로그 기반(log-based): 데이터 변경 내역을 기록한 붙임 전용 로그에서 추출. 변경 로그를 보관하는 저장소에서만 가능.
- 테이블 기반(table-based): 출력 큐 역할의 테이블에 변경분을 푸시하고 별도 프로세스가 그 테이블을 쿼리해 이벤트 스트림으로 보낸 뒤 엔트리를 삭제. 트랜잭션과 큐 메커니즘을 모두 지원하는 저장소에서만 가능.

세 패턴 모두 소스 레코드의 최근 업데이트 시간(updated_at) 컬럼으로 이벤트를 타임스탬프 순서대로 생산해야 한다. 프로듀서 발행 시간이 아니라 이벤트 발생 시간이 기록되어야 한다.

## 4.3 데이터 해방 프레임워크

카프카 커넥트(Kafka Connect), 아파치 고블린(Gobblin), 아파치 나이파이(NiFi) 같은 중앙화 프레임워크로 데이터를 추출할 수 있다. 다만 모든 해방에 전용 프레임워크가 필요한 것은 아니다. 프레임워크는 내부 데이터 모델을 외부에 노출시켜 결합도를 오히려 키우는 안티패턴을 조장할 수 있다.

## 4.4 쿼리로 데이터 해방

데이터 저장소를 쿼리해 결과를 이벤트 스트림으로 보낸다. 최초 1회 벌크 쿼리 후 주기적으로 증분 업데이트한다.

- 벌크 로딩: 전체 데이터를 한 번에 로드. 데이터가 작을 때만 실용적.
- 증분 타임스탬프 로딩: `updated_at` 컬럼으로 최근 변경분만 가져옴.
- 자동증가 ID 로딩: 마지막으로 처리한 ID 이후 레코드만 가져옴. 불변 레코드 테이블에 적합.
- 맞춤 쿼리: 여러 테이블 조인과 반정규화로 내부 데이터 모델을 격리.
- 증분 업데이트 운영: 타임스탬프나 자동증가 ID가 없으면 추가해야 하고, 둘 다 불가능하면 쿼리 기반 증분은 쓸 수 없다. 폴링 빈도가 너무 짧으면 직전 쿼리가 끝나기 전 다음 쿼리가 시작되어 옛 데이터가 새 데이터를 덮어 쓰는 경합 조건이 발생한다.

### 4.4.6 쿼리 기반 업데이트의 장점

- 맞춤성: 모든 데이터 저장소에 적용 가능하고 쿼리 옵션을 자유롭게 지정할 수 있다.
- 독립적인 폴링 주기: SLA가 엄격한 쿼리는 자주, 비용 큰 쿼리는 드물게 실행.
- 내부 데이터 모델 격리: 구체화 뷰나 쿼리 가능 객체로 내부 모델을 숨길 수 있다.

### 4.4.7 쿼리 기반 업데이트의 단점

- 최근 업데이트 시간 컬럼이 반드시 필요하다.
- 하드 삭제 추적 불가. 소프트 삭제 플래그 방식만 가능.
- 데이터 세트 스키마와 출력 이벤트 스키마 사이가 취약하게 연결된다. 데이터 정의 변경이 호환성을 깰 수 있다.
- 간헐적 캡처. 폴링 주기 사이의 여러 변경이 단일 이벤트처럼 보인다.
- 생산 리소스 낭비. 하부 시스템에 부하를 준다.
- 데이터 변경량에 따라 쿼리 성능이 출렁인다.

## 4.5 CDC 로그로 데이터 해방

데이터 저장소에 내장된 CDC 로그(예: MySQL 바이너리 로그, PostgreSQL 선행 기입 로그)를 활용한다. 모든 저장소가 불변 변경 로그를 제공하지는 않아 기술 선택 폭이 좁다.

로그는 무한정 보관하지 않으므로 처음에 부트스트래핑(bootstrapping)으로 기존 데이터 스냅샷을 찍어야 한다. 스냅샷의 마지막 레코드와 로그의 첫 레코드가 정확히 중첩되어야 누락이 없다. 이후 체크포인트를 두며 전진하면 적어도 한 번 이상 전달이 가능하다. 엔티티 데이터 업데이트는 멱등적이므로 중복 전달이 큰 문제가 되지 않는다.

데베지움(Debezium)이 대표적 도구로 카프카와 펄사에 변경 데이터를 생산할 수 있다.

### 4.5.1 데이터 저장소 로그의 장점

- 삭제 추적: 바이너리 로그에 하드 삭제가 포함되어 있어 그대로 삭제 이벤트로 변환.
- 데이터 저장소 성능 영향 최소화: 선행 기입 로그 기반은 추가 부하가 거의 없다.
- 저지연 업데이트: 로그에 기록되는 즉시 전파 가능.

### 4.5.2 데이터 저장소 로그의 단점

- 내부 데이터 모델이 체인지로그에 그대로 노출된다. 신중한 격리 작업이 필요하다.
- 데이터 저장소 외부에서 반정규화해야 한다. 다운스트림 마이크로서비스가 외래 키 조인을 떠안는다.
- 데이터 세트 스키마와 출력 이벤트 스키마 사이의 의존 관계가 취약하다.

## 4.6 아웃박스 테이블로 데이터 해방

내부 테이블 업데이트와 아웃박스 테이블 삽입을 단일 트랜잭션으로 묶어 데이터 정합성을 보장한다. 별도 프로세스가 아웃박스 테이블을 폴링해 이벤트 스트림으로 발행한 뒤 레코드를 삭제한다. 데이터 저장소나 애플리케이션 레이어 한 곳은 반드시 수정해야 하므로 CDC 로그 방식보다 침습적이지만, 정확한 단일 진실 공급원과 적어도 한 번 이상 전달을 보장한다.

같은 ID 레코드가 짧은 시간에 여러 번 업데이트될 수 있으므로 정렬 식별자(자동증가 ID)와 created_at 컬럼이 명확해야 한다.

### 4.6.1 성능 고려 사항

아웃박스 테이블이 있는 저장소와 애플리케이션에 추가 부하가 걸린다. 대규모 트래픽이라면 비용이 커지므로 CDC 로그 파싱 등 대안과 비교해 균형을 맞춰야 한다.

### 4.6.2 내부 데이터 모델 격리

아웃박스 테이블과 내부 테이블을 1대1로 매핑할 필요는 없다. 오히려 아웃박스 테이블의 핵심 가치는 클라이언트가 내부 데이터 모델을 다운스트림 컨슈머로부터 격리할 수 있다는 점이다. 내부 모델을 그대로 노출하는 것은 안티패턴이며, 컨슈머는 퍼블릭 데이터 규약으로 정의된 데이터에만 접근해야 한다.

데이터를 격리하는 방법은 두 가지다.

- 삽입 시점에 반정규화해 아웃박스 테이블에 퍼블릭 규약을 반영. 저장 공간과 성능 비용 발생.
- 1대1 매핑을 유지하고 별도의 이벤트화(eventification) 처리기로 다운스트림에서 반정규화. 프라이빗 네임스페이스의 정규화된 원본 스트림과 퍼블릭 네임스페이스의 반정규화된 스트림을 분리한다.

내부 데이터 모델 격리는 서비스 간 결합을 끊고, 시스템이 새 비즈니스 요건이 아닌 업스트림 내부 모델 변경에 끌려다니지 않도록 보장한다.

### 4.6.3 스키마 호환성 보장

직렬화 시점에 따라 트레이드오프가 달라진다.

- 사전 직렬화(아웃박스 트랜잭션 전): 직렬화 실패 시 트랜잭션도 함께 롤백되어 내부 테이블과 아웃박스 테이블이 항상 동기화된다. 가장 강력하지만 직렬화 오버헤드로 성능이 떨어질 수 있고, 직렬화 실패 시 비즈니스 작업이 진행되지 못한다.
- 사후 직렬화(아웃박스에 쓴 후 발행 시점): 트랜잭션 성공이 데이터 호환성을 보장하지 않으므로 직렬화 실패 이벤트가 쌓일 수 있다. 일부는 발행되고 일부는 막혀 출력 스트림의 이벤트 순서가 어긋날 수 있다.

아웃박스 테이블 방식의 장점은 다언어 지원, 사전 스키마 강화 가능, 내부 데이터 모델 격리, 반정규화 자유다. 단점은 애플리케이션 코드 변경 필수, 비즈니스 워크플로 성능 영향, 데이터 저장소 부하 증가다.

### 4.6.4 변경 데이터를 트리거로 캡처

AFTER 트리거로 변경된 행을 변경 데이터 테이블에 기록한다. 오래된 RDBMS에서 잘 작동하며 트리거가 실패하면 원래 커맨드도 실패해 원자성이 보장된다. 다만 트리거 안에서 출력 스키마 검증이 어렵고, 트리거 수가 늘수록 관리 비용이 빠르게 증가한다.

장점은 대부분의 RDB가 지원, 소규모 데이터일 때 낮은 오버헤드, 특정 필드만 노출하는 맞춤 로직이 가능하다는 점. 단점은 성능 오버헤드, 트리거를 빠뜨리면 내부 데이터와 해방된 데이터가 어긋날 위험, 확장성 부족, 사후 스키마 강화의 한계다.

## 4.7 데이터 정의 변경을 캡처 대상 데이터 세트로

DDL 변경(컬럼 추가, 삭제, 이름 변경, 타입 변경 등)은 다운스트림 컨슈머에게 큰 영향을 줄 수 있다. 각 패턴이 DDL 변경을 언제 감지하는지가 핵심이다.

- 쿼리 패턴과 CDC 로그 패턴: 이미 데이터 세트에 적용된 이후, 즉 사후에만 감지한다. 쿼리 시점이나 CDC 로그에서 새 스키마를 추론한 뒤 출력 이벤트 스트림 스키마와 비교한다. 데베지움은 현재 MySQL의 데이터 정의 변경만 지원한다.
- 변경 데이터 테이블 패턴: 소스 시스템 개발 주기와 통합되어 프로덕션 릴리스 전에 비교 검증이 가능하다. 검증 코드나 트리거가 어긋나면 변경 데이터 테이블에 데이터가 기록되지 않아 사고를 사전에 막는다.

캡처 대상 데이터 세트에서 유효한 변경이 해방된 이벤트 스키마 입장에서는 비호환 변경일 수 있다. 양방향 호환성이 필요한데 기본값 없는 널 금지 컬럼이 추가되면 옛 스키마 컨슈머가 처리할 수 없다.

## 4.8 이벤트 데이터를 데이터 저장소에 싱킹

반대 방향 작업이다. 이벤트 스트림을 소비해 데이터 저장소에 삽입하는 것을 싱킹(sinking)이라 한다. 이벤트 기반이 아닌 레거시 애플리케이션을 이벤트 스트림과 통합할 때 유용하며, 점대점 결합을 대체하는 용도로 쓰인다. 빅데이터 분석을 위해 HDFS 같은 분산 파일 시스템에 싱크하는 사례도 흔하다.

## 4.9 싱킹과 소싱의 비즈니스 영향도

중앙화 프레임워크는 낮은 오버헤드로 데이터를 해방할 수 있게 해주지만 두 가지 위험이 있다.

- 팀 상호 의존이 생긴다. 캡처할 시스템을 운영하는 팀과 프레임워크를 운영하는 팀이 분리되어 있어, 한쪽의 변경이 다른 쪽 커넥터에 영향을 주는데 그 사실은 프레임워크 팀만 감지할 수 있다.
- 시스템 자체의 이벤트 기반 전환을 막는다. CDC 프레임워크에 의존하면 조직은 데이터가 이벤트 스트림으로 나갔다는 사실만으로 만족하고 애플리케이션을 진짜 이벤트 기반으로 리팩터링하지 않는다.

CDC는 이벤트 기반 아키텍처의 종착지가 아니라 출발점이다. 가능한 한 CDC 프레임워크 의존을 줄이고 팀이 스스로 (아웃박스 패턴 같은 방식으로) CDC를 구현하도록 만들어야 한다. 이것이 이벤트를 일급 시민으로 보는 문화 전환이며, 이벤트 기반 마이크로서비스 도입의 핵심이다.

데이터 소유자는 자신이 생산하는 이벤트의 스키마, 데이터 모델, 순서, 지연, 정확성에 대한 SLA를 명확히 도출해야 한다.

## 4.10 마치며

데이터 해방은 접근성 좋은 데이터 통신 레이어를 만드는 단계다. 해방 전략은 스펙트럼으로 존재한다. 한쪽 끝에는 소스 시스템과 가깝게 통합되어 이벤트 발행을 일급 시민으로 다루는 전략이 있고, 다른 쪽 끝에는 소스 데이터 소유자가 거의 모르게 프레임워크가 데이터를 가져가는 고도로 리액티브한 전략이 있다. 후자는 스키마 깨짐과 내부 데이터 모델 노출이 자주 일어나 장기적으로 유지되기 어렵다. 데이터 해방이 성공할지는 결국 조직 문화에 달려 있으며, 데이터 소유자가 깨끗하고 신뢰할 이벤트 스트림을 만드는 책임을 진지하게 받아들여야 한다.
