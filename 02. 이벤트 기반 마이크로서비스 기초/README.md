# 02. 이벤트 기반 마이크로서비스 기초

이벤트 기반 마이크로서비스는 경계 콘텍스트를 구현하기 위해 만든 작은 애플리케이션이며, 이벤트 브로커를 매개로 완전히 비동기 방식으로 통신한다. 입력 이벤트 스트림에서 이벤트를 소비하면서 동시에 출력 이벤트 스트림의 프로듀서 역할을 한다. 2장은 이 구조를 떠받치는 기본 부품들을 정의한다. 토폴로지, 이벤트 구조, 테이블-스트림 이원성, 이벤트 브로커의 요건, 그리고 운영을 위한 컨테이너와 관리 시스템이다.

## 2.1 토폴로지 구성

토폴로지는 두 층위로 구분된다.

- 마이크로서비스 토폴로지: 단일 마이크로서비스 내부의 데이터 주도 연산. 변환, 집계, 필터링 같은 처리 흐름이다.

- 비즈니스 토폴로지: 여러 마이크로서비스와 이벤트 스트림, API의 집합. 1장에서 다룬 비즈니스 통신 구조가 그대로 비즈니스 토폴로지를 구성하는 요소다.

## 2.2 이벤트 콘텐츠

이벤트는 비즈니스 통신 구조 범위에서 발생한 모든 일이 될 수 있다. 송장 접수, 회의실 예약, 신입 사원 채용 같은 업무 사건이 모두 이벤트다.

이벤트는 발생한 사건의 기록물이다. 애플리케이션 로그와 비슷하지만, 단순 기록을 넘어 단일 진실 공급원이라는 점이 결정적 차이다. 따라서 이벤트는 사건을 정확히 나타내기 위해 필요한 모든 정보를 담아야 한다.

## 2.3 이벤트 구조

이벤트는 키와 값 쌍으로 표현된다. 세부 정보는 값에 보관하고, 키는 식별, 라우팅, 집계에 사용된다. 키는 모든 이벤트의 필수 필드는 아니다.

세 가지 유형이 있다.

- 키 없는 이벤트: 하나의 사실을 진술하는 형태. 키가 없다.
- 엔티티 이벤트: 키가 엔티티의 유일 ID이고, 값이 어느 시점의 속성과 상태다. 엔티티의 현재 상태는 마지막 엔티티 이벤트만 있어도 알 수 있어 이벤트 기반 아키텍처에서 특히 중요하다.
- 키 있는 이벤트: 키가 있지만 엔티티를 나타내지는 않는다. 이벤트 스트림을 파티셔닝해 데이터 지역성을 보장하는 용도로 쓰인다. 같은 키로 집계하면 결국 엔티티 이벤트로 귀결된다.

## 2.4 엔티티 이벤트에서 상태를 구체화

엔티티 이벤트 스트림을 순서대로 적용하면 키와 값 테이블에 업서트되며 상태 저장 테이블이 구체화된다. 반대로 테이블의 변경을 이벤트로 발행하면 다시 스트림으로 바꿀 수 있다. 이 양방향 관계를 테이블-스트림 이원성(table-stream duality)이라 한다. 이벤트 기반 마이크로서비스에서 상태를 생성하는 기본 원리이며, 어떤 컨슈머든 키 있는 이벤트 스트림을 읽어 자신의 로컬 상태 저장소로 구체화할 수 있게 만들어 준다. 프로듀서와 컨슈머가 직접 결합하지 않고도 상태를 공유한다.

삭제는 묘비 이벤트(tombstone)로 표현한다. 값이 null인 키 있는 이벤트이며, 다운스트림 컨슈머에게 해당 키를 삭제해야 함을 알리는 관례다.

컴팩션(compaction)은 키별로 가장 최근 이벤트 하나만 남기고 같은 키의 옛 이벤트를 제거하는 작업이다. 디스크 사용량과 현재 상태에 도달하기 위한 처리량을 줄여 주지만, 이벤트 이력을 포기해야 한다.

<img width="660" height="254" alt="image" src="https://github.com/user-attachments/assets/be28cf43-fe4d-4e42-b400-6709564de9b6" />

상태 유지는 이벤트 기반 아키텍처에서 일반적인 패턴이다. 과거의 비즈니스 결정이 현재의 결정에 영향을 미치기 때문에, 순수하게 상태가 없는 스트리밍만으로 비즈니스 모델 전체를 표현할 수 있는 경우는 거의 없다.

## 2.5 이벤트 데이터 정의와 스키마

이벤트 데이터는 서비스 간 통신 수단이자 구현체와 무관한 장기 보관소다. 따라서 프로듀서와 컨슈머가 데이터의 의미를 동일하게 해석할 수 있는 공통 언어가 필요하다. 이상적으로는 컨슈머가 프로듀서에게 묻지 않고도 콘텐츠를 해석할 수 있어야 한다.

아파치 아브로(Avro)와 구글 프로토콜 버퍼(Protobuf) 같은 직렬화 기술은 두 가지를 제공한다.

- 진화 프레임워크: 다운스트림 컨슈머가 코드를 바꾸지 않아도 스키마 변경을 안전하게 처리한다.
- 정형 클래스 생성: 스키마 데이터를 언어별 객체로 변환해 비즈니스 로직을 단순하게 만든다.

## 2.6 마이크로서비스 단일 작성자 원칙

이벤트 스트림은 정확히 하나의 생산 마이크로서비스를 가진다. 어떤 이벤트라도 데이터 계통을 따라가면 진실 공급원을 추적할 수 있다.

## 2.7 마이크로서비스를 이벤트 브로커로 강화

이벤트 브로커는 이벤트 기반 마이크로서비스 플랫폼의 핵심이다. 이벤트를 받아 큐나 파티션된 이벤트 스트림에 저장하고, 다른 프로세스가 소비하도록 제공한다. 일반적으로 다수의 분산 브로커가 한 클러스터로 동작하며, 다음 네 가지 기능을 제공한다.

- 확장성: 브로커 인스턴스를 추가해 생산과 소비, 스토리지 용량을 늘릴 수 있다.
- 보존성: 노드 간 데이터 복제로 한 브로커 장애에도 데이터가 보존된다.
- 가용성: 클러스터링 덕분에 한 브로커가 장애가 나도 클라이언트는 다른 노드에 접속할 수 있다.
- 고성능: 여러 노드가 부하를 분담해 초당 수십만 회 수준의 읽기와 쓰기를 처리한다.

### 2.7.1 이벤트 보관 및 처리

브로커가 사용할 하부 데이터 스토리지의 최소 요건은 다음과 같다.

- 파티셔닝: 이벤트 스트림을 하위 스트림으로 나눠 병렬 처리량을 높인다. 필수는 아니나 성능상 유리하다.
- 순서 보장: 파티션 내에서 데이터 순서가 보장된다.
- 불변성: 한 번 발행된 이벤트는 수정할 수 없다. 수정하려면 새 이벤트를 발행한다.
- 인덱싱: 발행 시점에 오프셋이 부여되며, 컨슈머는 오프셋으로 다음 읽기 위치를 특정한다. 컨슈머의 현재 인덱스와 마지막 인덱스의 간격이 컨슈머 랙(consumer lag)이다.
- 무기한 보존: 이벤트 스트림에서 상태를 관리하려면 무기한 보존이 가능해야 한다.
- 재연성(replayability): 어떤 컨슈머라도 필요한 데이터를 골라 다시 읽을 수 있어야 한다. 단일 진실 공급원의 근간이다.

### 2.7.2 추가 고려 사항

이벤트 브로커를 선택할 때 함께 따져야 할 항목들이다.

- 지원 도구: 이벤트와 스키마 데이터 조회, 쿼터와 접근 제어, 모니터링과 컨슈머 랙 측정.
- 호스티드 서비스: 매니지드 솔루션 가용 여부, 자체 호스팅과의 비용 비교, 재해 복구와 멀티존 배포 지원, 벤더 종속성.
- 클라이언트 라이브러리와 처리 프레임워크: 사용 중인 언어와 도구를 지원하는지가 핵심.
- 커뮤니티 지원: 기술 성숙도, 프로덕션 운영 사례, 인력 시장에서의 보편성.
- 장기 데이터 스토리지: 계층형 스토리지로 오래된 세그먼트를 저렴한 저장소(S3, GCS 등)로 옮길 수 있는지.

## 2.8 이벤트 브로커 대 메시지 브로커

메시지 브로커는 발행과 구독 메시지 큐를 제공하며, 프로듀서가 큐에 메시지를 쓰면 컨슈머가 받아 처리하고 ACK 직후 또는 짧은 시간 안에 삭제된다. 처음부터 이벤트 브로커와는 다른 문제를 풀기 위해 설계됐다.

이벤트 브로커는 메시지 브로커가 제공하지 못하는 두 가지를 충족한다.

- 전체 사본 제공: 메시지 브로커는 큐 단위로 처리해 여러 컨슈머가 같은 큐를 소비해도 각자 부분 집합만 받는다. 이벤트 브로커는 레코드 장부 하나를 두고 인덱스로 개별 접근을 관리해 여러 컨슈머가 각자 필요한 이벤트를 마음대로 읽는다.
- 무기한 보존과 재연: 메시지 브로커는 ACK 후 즉시 삭제하지만 이벤트 브로커는 업무상 필요한 기간 동안 보존하며 컨슈머가 로그의 특정 위치부터 재처리할 수 있다.

이벤트 브로커는 메시지 브로커를 대체할 수 있지만 그 반대는 불가능하다.

### 2.8.1 불변 로그에서 소비

이벤트 브로커는 일반적으로 붙임 전용 불변 로그를 사용한다. 이벤트는 로그 끝에 추가되며 자동 증가 인덱스가 부여된다. 소비 방식은 두 가지다.

- 이벤트 스트림으로 소비: 각 컨슈머가 자신의 오프셋을 독립적으로 관리한다. 컨슈머 그룹은 여러 컨슈머를 하나의 논리 엔티티로 묶어 파티션을 나눠 가지게 한다. 같은 그룹 안에서 활성 컨슈머 수는 파티션 수를 넘을 수 없다.
    
    <img width="625" height="294" alt="image" src="https://github.com/user-attachments/assets/7b6ba55b-c5fb-4a56-ae9a-9a7999e7a9c2" />

- 큐로 소비: 이벤트 하나를 단 하나의 마이크로서비스 인스턴스만 소비한다. 순서는 보장되지 않으며 모든 이벤트 브로커가 큐를 지원하지는 않는다 (예: 아파치 펄사는 지원, 아파치 카프카는 지원하지 않음).

### 2.8.2 단일 진실 공급원 제공

불변 로그는 단일 진실 공급원에 적합한 저장 메커니즘이다. 이벤트 브로커가 그 역할을 하려면 조직 문화도 바뀌어야 한다. 모놀리스 DB에 직접 SQL로 접근하던 관행에서 벗어나, 모놀리스 데이터도 반드시 이벤트 브로커로 발행해야 한다. 이벤트 스트림과 원본 DB 간 불일치는 곧 데이터를 생산하는 팀의 책임이며, 컨슈머는 더 이상 모놀리스에 접속하지 않고 이벤트 스트림에서 직접 데이터를 가져온다.

## 2.9 대규모 마이크로서비스 관리

마이크로서비스는 수가 늘수록 관리가 어려워진다. 서비스마다 컴퓨팅 리소스, 데이터 스토리지, 환경 변수가 다르고 팀별로 독립 관리와 배포가 필요하다. 그래서 컨테이너화나 가상화 기술을 컨테이너 관리 시스템(CMS)과 함께 사용한다.

- 컨테이너: 도커로 대중화된 기술. 호스트 OS 커널을 공유하면서 환경 변수와 디펜던시는 격리한다. 시동이 빠르고 리소스 오버헤드가 작지만, 커널을 공유하므로 한 컨테이너의 보안 결함이 전체에 영향을 줄 수 있다.
- 가상 머신(VM): 자체 OS와 하드웨어 가상화로 완전히 격리되어 보안에 강하지만 비용이 비싸고 시동이 느리며 공간을 더 차지한다. 구글 지바이저, 아마존 파이어크래커, 카타 컨테이너처럼 더 가벼운 VM 기술이 발전하면서 컨테이너와의 경계는 점차 흐려지고 있다.
- CMS: 컨테이너 배포, 리소스 할당, 수직/수평 확장을 담당한다. 쿠버네티스, 도커 엔진, 메소스 마라톤, 아마존 ECS, 노매드 등이 대표적이다.

각 마이크로서비스는 하나의 단위로 배포한다. 단일 컨테이너로 충분하지 않은 경우(예: 외부 저장소 연계가 복잡한 경우) 쿠버네티스 파드처럼 여러 컨테이너를 한 차례에 배포하는 장치를 사용한다.

## 2.10 마이크로서비스 세금 납부

마이크로서비스 아키텍처의 도구와 컴포넌트를 구현하는 데 들어가는 모든 비용(금전, 인력, 기회비용)을 마이크로서비스 세금(microservice tax)이라 한다. 이벤트 브로커, CMS, 배포 파이프라인, 모니터링, 로깅, 운영 비용이 모두 포함된다.

지불 방식은 두 가지다.

- 중앙(상위 부서) 지불: 일관된 프레임워크를 확보할 수 있다.
- 팀별 지불: 과도한 오버헤드, 솔루션 중복 도입, 도구 파편화, 지속 불가능한 성장을 초래할 수 있다.

이 세금은 이벤트 기반 마이크로서비스 도입의 가장 큰 걸림돌이 되곤 한다. 소규모 조직이라면 모듈화한 모놀리스 같이 비즈니스 요건에 더 맞는 아키텍처에 충실한 편이 낫고, 대규모 조직은 장기 비즈니스 목표에 비추어 충분한 기대 이익이 있는지 따져봐야 한다.

## 2.11 마치며

이벤트 브로커는 데이터 통신의 메인 메커니즘으로서 대규모 실시간 이벤트 스트림을 제공하며, 컨테이너화와 CMS 덕분에 마이크로서비스 역시 대규모로 운영할 수 있다.
