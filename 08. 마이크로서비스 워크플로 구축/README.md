# 08. 마이크로서비스 워크플로 구축

마이크로서비스는 비즈니스 워크플로의 한 부분만 담당하며, 여러 마이크로서비스가 모여 하나의 큰 워크플로를 이룬다. 8장은 그 구성 방식인 코레오그래피와 오케스트레이션, 그리고 두 패턴 위에서 분산 트랜잭션을 어떻게 다루는지, 트랜잭션이 불가능하거나 부적절할 때의 대안인 보상 워크플로를 다룬다.

## 8.1 코레오그래피 패턴

코레오그래피(choreography) 아키텍처는 고도로 분리된 마이크로서비스 구조다. 각 서비스는 업스트림 프로듀서나 다운스트림 컨슈머에 차단되거나 대기하지 않고 입력 이벤트가 도착하는 대로 반응한다. 모든 통신은 이벤트 스트림을 거치며 프로듀서는 자신의 데이터가 어디서 어떻게 소비되는지 모른다.

### 8.1.1 예제: 이벤트 기반 코레오그래피

서비스 A → B → C 형태의 단순한 코레오그래피 워크플로에서, 비즈니스 요건이 바뀌어 순서를 A → C → B로 재조정해야 한다고 가정한다. 두 서비스의 입력 스트림 매핑을 모두 바꿔야 하고, 스트림 안의 옛 데이터는 새 비즈니스 의미와 맞지 않을 수 있으므로 중대한 스키마 변경이 불가피하다. 새 스키마용 별도 스트림을 만들어야 할 수도 있다. 토폴로지 교체 전에 기존 워크플로의 미처리 이벤트를 모두 처리했는지 확인해야 한다.

### 8.1.2 코레오그래피 워크플로의 생성과 수정

워크플로 끝부분에 단계를 추가하기는 쉽지만 중간 삽입이나 순서 변경은 위험하다. 서비스 간 관계가 워크플로 콘텍스트 밖에서는 잘 보이지 않아 서비스 수가 늘수록 취약해진다. 비즈니스 기능이 여러 서비스에 분산되어 있으면 더 심해진다. 작은 비즈니스 로직 변경에도 여러 서비스를 함께 수정해야 할 수 있다.

### 8.1.3 코레오그래피 워크플로 모니터링

이벤트가 어디까지 진행됐는지, 어디서 막혔는지 한눈에 보기 어렵다. 중요한 워크플로는 각 출력 스트림을 상태 저장소로 구체화해 진행 상황을 추적할 필요가 있다.

워크플로 가시성은 관찰자에 따라 천차만별이다. 고객이 자기 주문의 결제와 배송만 보고 싶다면 세 스트림만 구체화하면 충분하다. 종단간 워크플로 전체를 보려면 수십 개의 스트림을 소비해야 하므로 변경이 잦은 환경에서는 모니터링이 까다롭다.

## 8.2 오케스트레이션 패턴

오케스트레이션(orchestration) 패턴은 중앙의 오케스트레이터 마이크로서비스가 하위 워커 서비스에 명령을 내리고 응답을 기다린다. 오케스트레이터는 워크플로 로직 전체를 알고 어느 파트가 완료, 진행 중, 미시작인지 추적한다.

비즈니스 수행 로직은 모두 워커 서비스 안에 둔다. 결제 3회 재시도 같은 로직은 결제 마이크로서비스의 경계 콘텍스트에 속하므로 오케스트레이터가 관여하지 않는다. 오케스트레이터는 결제 성공/실패만 알면 된다. 오케스트레이터에 비즈니스 로직을 끌어다 넣으면 유일신 서비스라는 안티패턴이 되며, 워크플로 비즈니스 로직이 흩어져 캡슐화가 깨지고 소유권 분리가 어려워진다.

### 8.2.1 예제: 이벤트 기반 오케스트레이션

오케스트레이터가 서비스 A, B, C로 명령 이벤트를 발행하고 응답을 구체화하면서 워크플로 단계를 추적한다.

### 8.2.3 직접 호출과 이벤트 기반 오케스트레이션 비교

이벤트 기반 워크플로는 다른 이벤트 기반 마이크로서비스와 같은 모니터링과 확장 도구를 그대로 쓸 수 있고, 외부 서비스도 이벤트 스트림을 자유롭게 소비할 수 있으며, 보존성과 재시도 내장으로 간헐적 실패에 강하다.

직접 호출 워크플로는 스트림 입출력 오버헤드가 없어 빠르지만, 간헐적 접속 문제는 오케스트레이터가 알아서 다뤄야 한다.

종속 서비스가 모두 SLA 범위 안에서 작동하고 신속한 응답이 필요하면 직접 호출이 적합하다. 보존성과 안정성이 우선이면 이벤트 기반이 적합하다. 실무에서는 메인 워크플로는 이벤트 기반, 외부 API는 직접 호출 식으로 혼용하는 경우가 많다.

### 8.2.4 오케스트레이션 워크플로의 생성과 수정

워크플로가 오케스트레이터 내부에만 정의되므로 한 군데서 변경할 수 있고, 진행 중인 이벤트를 중단시키지 않고도 워크플로를 바꿀 수 있는 경우가 많다. 단, 오케스트레이션은 결국 서비스를 단단히 결합시키므로 오케스트레이터와 워커의 관계를 명확히 정의해야 한다.

### 8.2.5 오케스트레이션 워크플로 모니터링

오케스트레이터의 구체화 상태를 쿼리하면 특정 이벤트의 진행 상황과 워크플로 이슈를 쉽게 파악할 수 있다. 모니터링과 로깅을 오케스트레이터 레벨에서 구현하면 장애를 일으키는 이벤트를 추적할 수 있다.

## 8.3 분산 트랜잭션

분산 트랜잭션(distributed transaction)은 둘 이상의 마이크로서비스에 걸친 트랜잭션이다. 트랜잭션 중단 시 처리한 내용을 되돌려야 하며, 이행과 역전 로직은 반드시 동일한 마이크로서비스 안에 둔다.

분산 트랜잭션은 시스템 동기화, 롤백 간소화, 인스턴스 장애 처리, 네트워크 연결 등 관심사가 많아 리스크와 복잡도를 키운다. 가능하면 피하되, 도입하지 않으면 더 큰 리스크가 생기는 경우에 한정한다.

이벤트 기반 아키텍처에서 분산 트랜잭션은 사가(saga)라 부르며, 코레오그래피나 오케스트레이션 패턴으로 구현한다. 정상 처리와 복구 액션은 모두 멱등적이어야 한다.

### 8.3.1 코레오그래피 트랜잭션: 사가 패턴

각 서비스가 자신이 변경한 내용을 롤백할 수 있어야 한다. 원래 느슨하던 서비스들이 결합되고, 무관하던 서비스 간에 강한 의존이 생길 수 있다.

서비스 A는 입력 이벤트의 원래 컨슈머로서 실패한 트랜잭션 결과를 처분한다. 컨슈머가 트랜잭션의 최종 상태를 파악하려면 성공 출력 스트림과 실패 트랜잭션 스트림을 모두 리스닝해야 한다. 진행 중이나 교착된 트랜잭션의 상태는 두 스트림만으로는 알 수 없으므로 각 이벤트 스트림을 구체화하거나 마이크로서비스 내부 상태를 API로 노출해야 한다.

단일 작성자 원칙은 여기서도 지켜야 한다. 두 개 이상의 서비스가 같은 이벤트 스트림에 발행해서는 안 된다.

코레오그래피 트랜잭션은 모니터링이 어렵고 취약하므로 워크플로 변경이 거의 없고 순서가 매우 중요한 2~3개 정도의 서비스에 적합하다.

### 8.3.2 오케스트레이션 트랜잭션

오케스트레이터가 워크플로의 어느 지점에서든 트랜잭션을 되돌리는 로직을 갖는다. 각 워커 서비스는 그에 대응하는 복구 액션을 제공한다. 타임아웃, REST API를 통한 사람의 입력, 워커의 실패 응답 등 다양한 신호로 트랜잭션을 중단할 수 있다. 오케스트레이터는 중앙 집중식이라 모든 트랜잭션의 진행과 상태를 자세히 모니터링할 수 있다.

롤백 후 이벤트 처분(재시도, 폐기, 애플리케이션 종료, 오류 이벤트 출력)은 오케스트레이터가 결정한다. 오케스트레이터는 자신도 프로듀서로서 트랜잭션 실패 이벤트를 단일 출력 스트림에 발행할 수 있다. 모든 출력을 한 스트림으로 소비할 수 있어 코레오그래피 패턴과 차별화된다.

각 마이크로서비스는 자신의 상태 변화와 롤백 후 일관성을 전적으로 책임지며, 오케스트레이터는 롤백 명령을 내리고 확답을 기다릴 뿐이다. 재시도 정책, 에러 처리, 간헐적 장애 관리는 모두 워커 서비스의 책임이다.

오케스트레이션 트랜잭션은 워크플로 변경이 유연하고 의존 관계가 잘 드러나며 모니터링이 명쾌하다. 코레오그래피로는 다루기 어려운 복잡한 워크플로에 적합하다.

## 8.4 보상 워크플로

모든 워크플로를 완벽히 되돌릴 필요는 없다. 실패 시 사후 조치로 상황을 수습하는 것이 비즈니스적으로 더 적절한 경우가 많다.

티켓 예약, 재고 기반 시스템이 전형적이다. 결제 처리 후 재고가 없음을 뒤늦게 알게 됐을 때, 엄격히 트랜잭션 롤백을 적용해 환불하고 주문 취소를 알리면 기술적으로는 맞지만 기업 이미지가 나빠진다. 보상 워크플로(compensating workflow)는 새 재고를 주문하고 배송 지연을 알린 뒤 할인 쿠폰을 제공하는 식으로 고객 만족을 우선한다. 항공사, 여행사, 공연 티켓 판매가 자주 사용하는 방식이다. 보상 워크플로가 항상 가능한 것은 아니지만 고객 대면 제품의 분산 워크플로에서 유용하다.

## 8.5 마치며

코레오그래피 패턴은 비즈니스 단위와 독립적인 워크플로 사이의 결합을 느슨하게 한다. 서비스 수가 적고 작업 순서가 거의 바뀌지 않는 단순한 워크플로와 단순한 분산 트랜잭션에 적합하다. 오케스트레이션 패턴은 가시성과 모니터링이 좋고 복잡한 분산 트랜잭션을 한 곳에서 수정 가능하다. 변경 가능성이 크고 독립적인 서비스가 많은 워크플로에 어울린다. 분산 트랜잭션이 필수는 아니다. 실패 시 보상 액션 처리 방법은 기술이 아니라 고객 대면 비즈니스의 성격이 결정한다.
