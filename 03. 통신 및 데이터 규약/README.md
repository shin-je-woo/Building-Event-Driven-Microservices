# 03. 통신 및 데이터 규약

이벤트 기반 시스템에서 이벤트는 사건과 그 이유를 정확히 기술하는 메시지이자 통신의 기본 단위다. 프로듀서가 생산한 메시지의 콘텐츠와 의미를 컨슈머가 정확히 되살릴 수 있도록 보장하는 것이 통신의 핵심 과제다. 3장은 그 보장을 위한 도구인 데이터 규약, 명시적 스키마, 스키마 진화, 그리고 이벤트 설계의 모범 사례를 정리한다.

## 3.1 이벤트 기반 데이터 규약

데이터 규약(data contract)은 프로듀서와 컨슈머가 모두 준수하는 일종의 계약서다. 두 요소로 구성된다.

- 데이터 정의(data definition): 생산할 필드, 타입, 자료 구조.
- 트리거 로직(triggering logic): 이벤트가 생성된 이유, 즉 이벤트를 일으킨 비즈니스 로직.

비즈니스 요건이 진화하면 데이터 정의도 바뀐다. 트리거 로직 변경은 원래 이벤트의 의미를 깨뜨리는 경우가 많아 데이터 정의 변경이 더 일반적이다. 데이터 정의를 바꿀 때는 다운스트림 컨슈머가 사용 중인 필드를 삭제하거나 변경하지 않도록 주의해야 한다.

### 3.1.1 명시적인 스키마를 규약으로 활용

데이터 규약을 강제하는 가장 좋은 방법은 이벤트마다 명시적 스키마를 정의하는 것이다. 그렇지 않으면 암묵적 스키마에 의존하게 되는데, 다음과 같은 문제를 일으킨다.

- 컨슈머마다 데이터 해석 방식이 달라져 단일 진실 공급원의 일관성이 깨진다.
- 프로듀서가 자신의 이벤트 정의가 변경됐다는 사실조차 모를 수 있다. 다운스트림 컨슈머가 실패하기 전까지 드러나지 않는다.
- 컨슈머가 처리해야 할 부담이 과도하게 커진다.

명시적 스키마는 프로듀서와 컨슈머 양쪽에 안정성을 제공한다.

### 3.1.2 스키마 정의 주석

스키마 안의 통합된 주석과 메타데이터는 이벤트 의미 전달에 필수다. 두 영역에서 특히 진가가 발휘된다.

- 이벤트 트리거 논리를 스키마 정의 맨 앞 블록 헤더에 명시.
- 특정 필드에 콘텍스트 부여 (예: datetime 필드가 UTC인지, ISO인지, 유닉스 타임인지 주석에 명시).

### 3.1.3 완전한 스키마 진화

스키마 진화 규칙을 명확히 두면 프로듀서와 컨슈머가 각자의 일정대로 애플리케이션을 업데이트할 수 있다. 호환성은 세 종류다.

- 정방향 호환성(forward compatibility): 새 스키마로 생성한 데이터를 옛 스키마로 읽을 수 있다. 시스템 변경은 보통 프로듀서가 먼저 업데이트하면서 시작되므로 이벤트 기반 아키텍처에서 특히 유용하다.
- 역방향 호환성(backward compatibility): 옛 스키마로 생성한 데이터를 새 스키마로 읽을 수 있다. 컨슈머가 프로듀서보다 먼저 새 스키마를 릴리스해야 하는 경우, 휴대폰 같은 고객 하드웨어에서 옛 이벤트가 계속 흘러오는 경우, 옛 데이터를 재처리해야 하는 경우에 필요하다.
- 양방향 호환성(full compatibility): 정방향과 역방향의 조합. 가능한 한 항상 적용한다. 나중에 호환성을 완화하기는 쉽지만 높이기는 어렵기 때문이다.

스키마 진화 없이는 프로듀서와 컨슈머를 세밀하게 동기 조정해야 하므로 마이크로서비스의 독립 릴리스 원칙에 반한다.

### 3.1.4 코드 생성기 지원

코드 생성기(code generator)는 스키마를 특정 언어의 클래스 정의로 변환한다. 프로듀서는 이 클래스로 이벤트 객체를 만들고 시리얼라이저가 스키마에 명시된 타입과 널 금지 필드를 검증한다. 컨슈머는 이벤트를 받아 인코딩된 스키마 버전으로 역직렬화하고, 진화 규칙에 따라 자신이 지원하는 버전으로 변환한다. 누락된 필드는 기본값으로 채우고 미사용 필드는 제거한다.

이벤트 스키마를 메시지 안에 직접 넣으면 비용이 크므로 보통 스키마 레지스트리(schema registry)에 저장하고 온디맨드로 접근한다.

컴파일 언어에서는 타입 위반이나 널 금지 필드 누락을 컴파일 단계에서 잡아낼 수 있어 이벤트 정의를 안전하게 만든다.

### 3.1.5 중대한 스키마 변경

원래 도메인 모델 자체를 바꿔야 하는 큰 변화가 일어나면 스키마 진화 규칙으로 흡수할 수 없는 중대한 변경이 발생한다. 가급적 빨리 다운스트림 컨슈머와 소통해야 하며, 마이그레이션 계획에 관련자 전원의 공감대가 필요하다.

엔티티의 중대한 스키마 변경 적용 방법은 두 가지다.

- 옛 스키마와 새 스키마를 함께 둔다. 프로듀서에겐 가장 쉽지만 컨슈머가 두 정의를 알아서 해석하게 방치하는 셈이라 처리 일관성이 깨진다.
- 모든 엔티티를 새 스키마로 재생성한다. 프로듀서가 옛 엔티티의 출처인 소스 데이터를 재처리해 새 비즈니스 로직을 적용한다. 더 어렵지만 일관성을 보장한다. 옛 엔티티는 검증과 증빙용으로 원래 스트림에 그대로 두고 새 스트림에 업데이트된 엔티티를 발행한다.

비엔티티 이벤트는 더 간단하다. 새 이벤트 스트림을 만들어 거기에 새 이벤트를 생산하고, 옛 스트림 컨슈머가 새 스트림으로 등록하도록 미리 알린다. 옛 스트림은 보존 기간이 지난 뒤 삭제한다. 한 이벤트 스트림에 호환되지 않는 여러 이벤트 타입을 절대 섞지 않는다.

## 3.2 이벤트 포맷 선택

이벤트 데이터는 아브로(Avro), 스리프트(Thrift), 프로토콜 버퍼(Protocol Buffers)처럼 엄격하게 정의된 포맷을 사용하는 편이 좋다. 카프카와 펄사 같은 주요 이벤트 브로커 프레임워크가 모두 지원한다.

JSON 같은 단순 키-값 포맷은 키-값 구조는 있지만 명시적 스키마와 진화 프레임워크가 없어 팀 간 소통 비용을 늘리고 마이크로서비스의 격리성을 훼손한다. 비구조 일반 텍스트는 더 심각하다. 스키마 진화를 완벽히 지원하는 아브로나 프로토콜 버퍼가 권장된다.

## 3.3 이벤트 설계

이벤트 설계에는 모범 사례와 안티패턴이 존재한다. 절대 규칙은 아니지만 도메인의 함축된 의미와 트레이드오프를 고려해 신중히 선택해야 한다.

### 3.3.1 오직 진실만을 말할지어다

잘 정의된 이벤트는 그저 “뭔가 일어났음”을 전하는 메시지가 아니라, 이벤트 발생 동안의 모든 사실을 빠짐없이 기술한다. 입력 데이터에 비즈니스 로직을 적용한 결과 데이터이며, 단일 진실 공급원으로 간주된다. 컨슈머는 다른 데이터 출처를 통해 그 이벤트의 사실성을 확인할 필요가 없다.

### 3.3.2 스트림당 이벤트 정의는 하나만 사용

이벤트 스트림에는 하나의 논리적 이벤트 정의만 포함되어야 한다. 종류가 다른 이벤트들을 한 스트림에 섞으면 스트림 정체성이 흐려지고 새 스키마가 동적으로 추가될 수 있어 유효성 검증이 어려워진다.

### 3.3.3 가장 좁은 범위의 데이터 타입 사용

이벤트 데이터 타입은 가장 범위가 좁은 것을 쓴다. 그래야 코드 생성기와 타입 체크, 직렬화 테스트로 경계를 검증할 수 있다. 흔한 안티패턴은 다음과 같다.

- 문자열로 숫자 값 저장: 컨슈머가 파싱할 때 null 값이나 공백 문자열로 오류 가능성이 높아진다.
- 정수를 불리언으로 사용: 0과 1만 의미가 있다면 2나 -1은 무엇을 의미하는지 알 수 없다.
- 문자열을 이늄(enum)으로 사용: 오탈자와 부정확한 값이 끼어들 수 있고, 컨슈머가 유효값 범위를 사전 협의 없이는 알 수 없다. 암묵적 정의이므로 나쁜 습관이다.

이늄 자체도 조심해서 써야 한다. 프로듀서가 새 이늄 토큰을 추가했을 때 컨슈머가 모르는 값을 받아 처리해야 하기 때문이다. 프로토콜 버퍼와 아브로는 알 수 없는 이늄 토큰을 우아하게 처리하는 방법을 제공한다.

### 3.3.4 이벤트는 하나의 목적만 갖도록

타입 매개변수를 추가해 한 이벤트 정의로 여러 종류의 사건을 다루는 것은 흔한 안티패턴이다. 처음에는 단순해 보이지만 다음과 같은 문제가 누적된다.

- 기술적 표현형은 같아도 비즈니스 의미가 근본적으로 다르며, 그 의미가 시간이 지나며 달라진다.
- 타입별로 필요한 매개변수가 늘어나면서 nullable 필드가 누적되고 스키마가 비대해진다.
- 컨슈머는 자신과 무관한 데이터를 걸러내는 부가 로직을 매번 작성해야 한다.
- 데이터 규약 변경이 무관한 컨슈머에게도 영향을 준다.

다양한 타입 매개변수가 들어 있는 제네릭 이벤트가 필요하다는 것은 곧 경계 콘텍스트가 제대로 정의되지 않았다는 신호다.

예제: 도서와 영화를 다루는 웹사이트에서 사용자 이용 현황을 추적하기 위해 처음에는 `ProductEngagement` 하나에 `productType`과 `actionType` 이늄을 두는 식으로 설계할 수 있다. 영화 예고편 시청 여부, 도서 책갈피 페이지 같은 요건이 추가될 때마다 특정 타입에만 의미가 있는 nullable 필드가 늘어난다. 결과적으로 단일 책임 원칙에 따라 `MovieClick`, `BookClick`, `BookBookmark` 같이 이벤트를 분리하면 이늄과 nullable 필드가 사라지고 스키마가 평평해진다. 스트림과 이벤트 정의를 1대1로 유지하면 이벤트 정의는 시간이 지나도 표류하지 않는다.

### 3.3.5 이벤트 크기 최소화

이벤트는 작고 잘 정의되어 있어야 한다. 큰 이벤트를 설계해야 한다면 다음을 점검한다.

- 모든 데이터가 이 이벤트와 직접 관련 있는가, 아니면 만일을 위한 부가 데이터인가.
- 모든 데이터가 정말 관련 있다면 마이크로서비스가 너무 많은 일을 하고 있는지, 경계 콘텍스트를 다시 봐야 하는지 검토한다.

큰 이진 데이터(예: 고해상도 이미지)는 어쩔 수 없는 경우만 다루며, 외부 포인터로 가리키는 방식은 진실 공급원이 둘로 쪼개지고 페이로드가 가변적이 되므로 가급적 피한다.

### 3.3.6 미래의 컨슈머도 이벤트 설계에 반영

새 이벤트를 설계할 때는 컨슈머가 될 부서와 협의해 그쪽의 요건과 향후 비즈니스 기능을 확인한다. 컨슈머가 어떤 데이터가 인입될지 더 잘 알고 있기 때문이다.

### 3.3.7 이벤트를 세마포어나 시그널로 사용하지 않는다

작업 완료를 알리는 신호용으로만 쓰는 이벤트는 단일 진실 공급원이 아니다. 실제 작업 결과를 별도 위치에서 가져와야 한다면 진실 공급원이 두 개가 되어 일관성이 깨진다.

## 3.4 마치며

비동기식 이벤트 기반 아키텍처는 이벤트 품질에 크게 의존한다. 명시적 스키마와 트리거 로직, 주석과 메타데이터가 갖춰진 고품질 이벤트가 조직 전체에 이벤트 기반 아키텍처를 보급시키는 토대가 된다. 이벤트 정의는 범위를 좁혀 도메인에 집중하게 만들고, 스키마 진화는 도메인 모델 변경을 안전하게 흡수하는 메커니즘이 된다. 중대한 변경이 불가피한 경우 이해 관계자가 함께 모여 미래의 도메인 모델을 다듬어야 한다.
