# 06. 확정적 스트림 처리

여러 파티션에서 이벤트를 소비하는 마이크로서비스가 실시간 처리와 재처리에서 동일한 결과를 내도록 만드는 것이 확정성(determinism)이다. 6장은 이 목표를 위한 도구를 다룬다. 타임스탬프와 이벤트 스케줄링, 워터마크와 스트림 시간, 비순차 이벤트와 지각 이벤트 처리 전략, 재처리 절차, 그리고 간헐적 실패와 프로듀서-브로커 연결 문제다.

## 6.1 이벤트 기반 워크플로의 확정성

마이크로서비스의 두 가지 처리 상태가 있다. 실시간에 가깝게 처리하는 상태(주로 실행 시간이 긴 서비스)와 과거 이벤트부터 따라잡는 상태(주로 신규 서비스). 컨슈머 오프셋을 처음 시점으로 되감고 재시작했을 때 처음과 같은 결과가 나와야 확정적이라 할 수 있다.

완벽한 확정성은 불가능하다. 월클럭 시간 기반 서비스나 외부 시스템을 쿼리하는 서비스는 본질적으로 비확정적이다. 모든 이벤트가 제때 도착하고 장애가 없는 이상적 환경은 존재하지 않으므로, 가능한 한 확정에 가까운 결과를 내도록 최선을 다하는 것이 현실적 목표다.

## 6.2 타임스탬프

이벤트 스트림에 저장된 이벤트는 오프셋과 타임스탬프를 함께 가진다. 오프셋은 컨슈머가 어디까지 읽었는지, 타임스탬프는 이벤트 발생 시점을 기록한다. 분산 시스템에서 이벤트 처리 순서를 비교하려면 일관성 있고 동기화된 타임스탬프가 필수다.

타임스탬프 종류는 네 가지다.

<img width="938" height="478" alt="image" src="https://github.com/user-attachments/assets/d686939a-8ffa-47a8-952d-c98661f81800" />

- 이벤트 시간(event time): 발생 시점에 프로듀서가 할당한 로컬 타임스탬프.
- 브로커 인입 시간(broker ingestion time): 브로커가 이벤트를 받은 시간. 이벤트 시간이나 인입 시간 중 설정 가능. 프로듀서 시간을 신뢰할 수 없을 때 대안으로 쓴다.
- 컨슈머 인입 시간(consumer ingestion time): 컨슈머가 이벤트를 받은 시간.
- 처리 시간(processing time): 컨슈머가 처리를 완료한 월클럭 시간.

### 6.2.1 분산 타임스탬프 동기화

독립된 두 시스템 클럭을 완전히 같게 맞추는 것은 물리적으로 불가능하다. NTP(Network Time Protocol)로 거의 동기화할 수 있고, NTP 서버 개선과 GPS 활용 덕분에 정확도가 1밀리초 미만까지 향상됐다. 그래도 소소한 순서 꼬임은 여전하므로 시스템 클럭에 100% 의존해서는 안 된다.

### 6.2.2 타임스탬프 찍힌 이벤트 처리

여러 스트림과 파티션에 분산된 이벤트를 일관된 시간 순서로 처리하기 위해 타임스탬프가 필요하다. 오프셋 순서 비교는 단일 파티션 안에서만 유효하다. 라운드 로빈 같은 단순 방식으로 여러 파티션을 소비하면 발생 순서를 잃어 결과가 부정확해질 수 있다. 예금과 인출이 별도 스트림인 은행 시스템에서 발생 순서를 무시하면 초과 인출 수수료가 잘못 부과될 수 있다.

## 6.3 이벤트 스케줄링과 확정적 처리

이벤트 스케줄링(event scheduling)은 여러 입력 파티션에서 다음에 처리할 이벤트를 선택하는 로직이다. 일반적 구현은 할당된 전체 파티션에서 타임스탬프가 가장 오래된 이벤트부터 하나씩 다운스트림으로 전달하는 방식이다. 비즈니스 로직이 처리 순서에 민감하면 마이크로서비스에 이벤트 스케줄링 기능을 반드시 구현해야 한다. 기본 컨슈머에는 이 기능이 빠져 있는 경우가 많다.

### 6.3.1 맞춤 이벤트 스케줄러

아파치 삼자(Apache Samza)의 MessageChooser 인터페이스 같은 맞춤 스케줄러를 쓸 수 있다. 다만 맞춤 스케줄러는 비확정적 속성을 갖기 쉬워 재연 가능한 결과를 보장하지 못할 수 있다. 직접 구현할 때는 주의가 필요하다.

### 6.3.2 이벤트 시간, 처리 시간, 인입 시간 중 선택

실무에서는 로컬 시스템이 할당한 이벤트 시간이 가장 정확하다. 프로듀서 타임스탬프를 신뢰할 수 없으면 브로커 인입 시간을 쓰는 것이 차선이다. 월클럭과 컨슈머 인입 시간은 실행 시점에 따라 달라지므로 확정적 처리에 적합하지 않다.

### 6.3.3 컨슈머의 타임스탬프 추출

타임스탬프 추출기(timestamp extractor)로 이벤트에서 타임스탬프를 꺼낸다. 키, 값, 메타데이터 어디에 있든 추출 가능하며, 추출된 시간은 처리 내내 일관되게 사용된다.

### 6.3.4 외부 시스템에 요청-응답 호출

토폴로지 안에서 외부 시스템에 동기 호출을 하면 비확정적 결과가 나올 수 있다. 외부 시스템의 내부 상태는 마이크로서비스가 통제할 수 없기 때문이다. 비즈니스 요건에 따라 수용 여부를 판단해야 한다.

## 6.4 워터마크

워터마크(watermark)는 처리 토폴로지 안에서 이벤트 시간의 진행을 추적하는 신호다. "시간 T 이전의 모든 이벤트가 처리됐다"를 다운스트림 노드에 알린다. 노드가 워터마크를 받으면 내부 이벤트 시간을 업데이트하고 다음 노드로 전파한다. 워터마크는 일정 주기나 일정 개수의 이벤트 처리 후마다 새로 만들어진다. 아파치 스파크, 플링크, 삼자, 빔에서 통용되는 기법이다.

### 6.4.1 병렬 처리 시 워터마크

여러 컨슈머 인스턴스 사이에서 이벤트 시간을 조정할 때 유용하다. groupByKey 같이 여러 업스트림에서 입력을 받는 노드는 자신의 이벤트 시간을 모든 입력 소스의 이벤트 시간 중 최솟값으로 잡는다. 워터마크는 자기 값보다 작은 타임스탬프 이벤트가 지각 이벤트라는 사실을 알릴 뿐, 노드의 스케줄링에는 영향을 주지 않는다.

스파크, 플링크, 빔에서 대규모 스트림을 셔플하려면 전용 클러스터가 필요하다. 리파티션 같은 작업은 이벤트 브로커의 스트림이 아니라 클러스터 내부 통신으로 수행된다.

## 6.5 스트림 시간

스트림 시간(stream time)은 아파치 카프카 스트림즈가 시간을 유지하는 방식이다. 컨슈머 애플리케이션이 토폴로지 전체에 걸쳐 단일한 스트림 시간(처리한 이벤트 중 가장 높은 타임스탬프)을 유지한다. 컨슈머 인스턴스는 각 입력 파티션에서 이벤트를 받아 버퍼링하고, 스케줄링 알고리즘으로 다음 처리할 이벤트를 고른다. 스트림 시간은 절대로 감소하지 않는다.

각 이벤트를 완전히 처리한 뒤 다음 이벤트로 넘어가며 깊이 우선 방식으로 진행된다. 리파티션 스트림이 있으면 토폴로지를 둘로 쪼개 각 하위 토폴로지가 자체 스트림 시간을 유지한다. 워터마크가 각 노드별로 독립적인 시간을 유지하는 것과 근본적으로 다른 방식이다.

### 6.5.1 병렬 처리 시 스트림 시간

리파티션이 필요한 작업은 카프카 스트림즈에서 내부 이벤트 스트림(internal event stream)을 통해 이벤트 브로커로 회송된다. 인스턴스가 그것을 다시 소비하면서 키별로 같은 파티션에 모이게 된다. 별도 셔플 클러스터가 필요 없어 마이크로서비스 친화적이다. 리파티션 시 이벤트 시간은 그대로 보존되어야 한다. 월클럭으로 덮어쓰면 시간 순서가 파괴된다.

## 6.6 비순차 이벤트와 지각 이벤트

비순차 이벤트(out-of-order event)는 이벤트 스트림에서 앞에 있는 이벤트보다 타임스탬프가 작은 이벤트다. 지각 이벤트(late event)는 컨슈머가 정한 데드라인을 지나 도착한 이벤트다. 같은 비순차 이벤트라도 마이크로서비스의 관대함에 따라 지각으로 판정되기도 하고 그렇지 않기도 한다.

배치로 처리하는 유한 데이터 세트는 비순차 이벤트가 와도 비교적 유연하게 대응할 수 있지만 지연이 길다. 무한 데이터 세트(이벤트 스트림)에서는 마이크로서비스 설계 단계에서 지연과 확정성 요건을 결정해야 한다. 이는 기술이 아닌 비즈니스 요건이다.

### 6.6.1 워터마크와 스트림 시간에서 늦은 이벤트의 정의

- 워터마크 방식: 워터마크 W(t) 이후에 도착한 이벤트 시간 t' < t의 이벤트가 늦은 이벤트다. 해당 노드가 알아서 처리.
- 스트림 시간 방식: 스트림 시간이 t로 증가한 이후에 도착한 t' < t 이벤트가 늦은 이벤트다. 하위 토폴로지의 각 처리기가 알아서 처리.

### 6.6.2 비순차 이벤트의 원인

- 비순차 데이터에서 소싱: 원본 스트림 자체가 순서가 어긋나 있거나 외부 시스템의 타임스탬프가 어긋난 경우.
- 여러 프로듀서가 여러 파티션에 쓰기: 리파티션 시 인스턴스마다 독립적인 스트림 시간을 유지하므로 시간 갭(time skew)이 생긴다. 파티션 크기 불균형이나 처리율 차이, 큰 이벤트 백로그가 있을수록 심해진다.

### 6.6.3 시간에 민감한 함수와 윈도잉

윈도잉(windowing)은 이벤트를 시간 기준으로 그룹핑하는 것이다. 세 가지 종류가 있다.

- 텀블링 윈도(tumbling window): 크기가 고정되고 서로 겹치지 않는다. "사용자가 제품을 가장 많이 이용하는 시간대는?" 같은 질문.
- 슬라이딩 윈도(sliding window): 크기는 고정되지만 윈도 슬라이드 증분만큼 서로 겹친다. "지난 한 시간 동안 광고를 클릭한 사용자 수?"
- 세션 윈도(session window): 크기가 동적으로 변한다. 활동 부재 타임아웃으로 닫히고, 새 활동이 재개되면 새 세션이 시작된다. "사용자가 한 브라우저 세션 동안 본 것?"

스트림 처리의 근본적 한계는 모든 이벤트를 빠짐없이 수신했다고 단정할 수 없다는 점이다. 비순차 이벤트를 얼마나 기다릴지, 어느 시점에 포기할지 결정해야 한다.

## 6.7 지각 이벤트 처리

지각 이벤트 처리 전략은 비즈니스 수준에서 결정되어야 한다. 금융 거래는 어디서든 반드시 처리하지만 일시 측정값은 폐기해도 된다. 일반적 방법은 세 가지다.

- 이벤트 폐기(drop event): 그냥 버린다. 윈도가 닫히면 집계 종료.
- 대기(wait): 일정 시간 동안 윈도 결과 출력을 미룬다. 지연이 늘지만 확정성이 높아진다.
- 유예 기간(grace period): 윈도가 완료되면 결과를 일단 출력하고 유예 기간 동안 윈도를 가용 상태로 유지. 지각 이벤트가 도착할 때마다 집계를 업데이트해 새 결과를 출력한다.

처리 가이드라인을 정할 때 점검할 질문들이 있다. 지각 이벤트 발생 가능성은? 얼마나 기다려야 하나? 누락 시 비즈니스 영향은? 대기로 얻는 이익은? 상태 저장에 필요한 리소스는? 대기 비용이 이익을 능가하는가?

## 6.8 재처리 대 준실시간 처리

불변 이벤트 스트림은 오프셋을 되감아 임의 시점부터 처리를 재연할 수 있다. 재처리는 보통 이벤트 시간 기반 마이크로서비스에서 수행하며, 월클럭 시간 기반 집계나 윈도잉을 쓰는 서비스에서는 쓰지 않는다.

재처리 절차는 다음과 같다.

1. 시점을 정한다. 상태 저장 컨슈머는 보통 각 입력 스트림의 맨 처음부터 재처리하는 것이 모범 사례다. 엔티티 스트림은 특히 중요한 팩트를 담고 있어 처음부터 처리해야 한다.
2. 어느 컨슈머 오프셋을 리셋할지 결정한다. 상태 저장 처리에 쓰이는 스트림은 맨 처음으로 되돌려야 한다. 엉뚱한 위치에서 시작하면 정확한 상태를 보장할 수 없다.
3. 데이터량을 확인한다. 재처리 시간을 가늠하고, 브로커 I/O를 독점하지 않도록 쿼터를 두거나 다운스트림에 사전 통보하고 자동확장 설정도 점검한다.
4. 재처리 시간을 고려한다. 중단 시간을 미리 계산하고, 컨슈머 인스턴스를 늘려 병렬도를 최대화한 뒤 끝나면 다시 축소한다.
5. 영향도를 살핀다. 재처리 중에 하면 안 되는 작업이 있는지 확인한다. 배송 완료 이메일을 재처리 때 다시 보내는 사고가 대표적이다.

## 6.9 간헐적 실패와 지각 이벤트

실시간 처리 중에는 이벤트가 늦을 수 있지만 재처리 중에는 같은 이벤트가 스트림 안에서 예상대로 사용 가능하다. 업스트림 문제가 다운스트림 컨슈머에 영향을 미치는 경로를 잘 보여주는 사례이며 감지하기 어려울 수 있다.

## 6.10 프로듀서-이벤트 브로커 연결 문제

프로듀서가 일시적으로 브로커에 접속하지 못하면 이벤트는 발생 시점의 타임스탬프를 그대로 단 채 큐에 쌓인다. 접속이 복구되면 밀린 이벤트가 발행되는데, 실제 발생 순서대로 발행되더라도 월클럭 지연 때문에 준실시간 컨슈머에게는 지각 이벤트로 보인다.

해결책 두 가지가 있다. 이벤트 처리 전에 미리 정해진 시간 동안 대기하는 방식은 지연 비용이 들고 생산 지연이 대기 시간보다 짧을 때만 효과가 있다. 더 견고한 방식은 비즈니스 로직에 영향이 없도록 지각 이벤트 처리 로직을 컨슈머 코드에 단단히 구현하는 것이다.

## 6.11 마치며

무한 이벤트 스트림에서 완벽한 확정성은 본질적으로 불가능하다. 가장 합리적인 해법은 지연과 정합성의 트레이드오프를 비즈니스 요건에 맞춰 최적화하는 것이다. 비순차 이벤트와 지각 이벤트는 워터마크와 스트림 시간으로 식별하고 처리하며, 처리 전략(폐기, 대기, 유예 기간)은 데이터의 비즈니스 중요도에 따라 결정한다.
