# 09. FaaS 응용 마이크로서비스

FaaS(Function as a Service)는 트리거 조건이 발생하면 실행되는 함수 단위로 비즈니스 기능을 구성하는 서버리스 모델이다. 함수는 시작, 실행, 종료 사이클을 짧게 반복하며 부하에 따라 인스턴스 수를 유연하게 조정한다. 미리 정해진 시간이 지나면 항상 종료되고 모든 연결과 상태가 함께 사라진다는 점이 설계의 핵심 제약이다.

## 9.1 함수 기반 솔루션을 마이크로서비스로 설계

### 9.1.1 엄격한 경계 콘텍스트의 멤버십 관리

모든 함수와 내부 이벤트 스트림은 명확한 경계 콘텍스트에 소속되어야 한다. 함수를 너무 잘게 쪼개면 경계가 흐려진다. 함수-콘텍스트 매핑 메타데이터를 엄격히 관리하고, 콘텍스트별 리포지터리 안에서 코드를 운영하는 것이 좋다.

### 9.1.2 처리 완료 이후에만 오프셋 커밋

오프셋은 함수가 시작될 때가 아니라 처리가 완료된 뒤에 커밋한다. 처리 전 커밋은 재시도 실패 시 데이터 손실로 이어진다. 데이터 손실에 민감한 서비스라면 처리 완료 후 커밋만 사용한다.

### 9.1.3 적을수록 좋다

함수를 잘게 나누면 솔루션이 파편화되고 소유권이 모호해진다. 같은 콘텍스트의 작업이라면 여러 함수보다 함수를 적게 두는 편이 테스트, 디버깅, 관리 모두 쉽다.

## 9.2 FaaS 공급자 선택

오픈 소스(오픈위스크, 오픈FaaS, 쿠블리스, 누클리오)와 클라우드 서비스(AWS, GCP, Azure)가 있다. 클라우드 솔루션은 자사 이벤트 브로커에 특화되어 있고 보존 기간이 7일로 제한되는 단점이 있다. 이미 해당 클라우드를 쓰고 있다면 진입 오버헤드가 낮다.

## 9.3 함수를 마이크로서비스로 개발

함수 기반 솔루션의 네 컴포넌트는 함수, 입력 이벤트 스트림, 트리거 로직, 메타데이터(에러와 확장 정책)다. 함수-트리거 맵에는 컨슈머 그룹, 컨슈머 프로퍼티(배치 크기, 배치 윈도), 재시도와 에러 처리 정책, 확장 정책이 포함된다.

## 9.4 콜드 스타트와 웜 스타트

콜드 스타트는 컨테이너 시작, 코드 로드, 브로커 연결, 외부 리소스 연결을 모두 거치는 첫 실행이다. 대부분의 FaaS 프레임워크는 종료된 함수 인스턴스를 가능하면 재사용한다. 일시 중지된 함수가 트리거로 깨어나면 곧바로 처리를 재개할 수 있다.

## 9.5 트리거로 함수 시동

### 9.5.1 새 이벤트에 반응해 트리거: 이벤트-스트림 리스너

이벤트 스트림에 이벤트가 생성되면 함수를 트리거한다. 동기 트리거는 처리 순서를 보장하지만 병렬 처리를 제약한다. 비동기 트리거는 빠르지만 순서를 보장하지 않으므로 순서가 중요하지 않은 경우에만 쓴다. 배치 크기와 배치 윈도로 함수 시작 오버헤드를 분산한다.

### 9.5.2 컨슈머 그룹 랙에 반응해 트리거

컨슈머 그룹의 랙(헤드 오프셋과 현재 오프셋의 차이)을 폴링하여 함수를 트리거한다. 함수가 직접 브로커에 연결하여 이벤트 소비, 오프셋 커밋까지 챙겨야 한다. 기본 프로듀서/컨슈머 클라이언트에 가까운 방식이다.

### 9.5.3 스케줄에 따라 트리거

지정된 주기나 시각에 함수를 시동한다. 폴링 주기가 짧을수록 SLA에 유리하지만 브로커와 FaaS 프레임워크 부담이 커진다.

### 9.5.4 웹훅에 반응해 트리거

함수를 직접 호출해 시작한다. 모니터링 프레임워크, 스케줄러, 서드파티와 맞춤 연계에 쓴다.

### 9.5.5 리소스 이벤트에 반응해 트리거

DB 행이나 파일 시스템의 생성, 수정, 삭제로 함수를 트리거한다. 외부 데이터 소스 연계(예: FTP)에 유용하다.

## 9.6 비즈니스 업무를 함수로 처리

FaaS는 상태가 없거나, 여러 스트림의 확정적 처리가 불필요하거나, 큐 처리처럼 확장 폭이 큰 단순 토폴로지에 잘 맞는다. 동시성과 확정성이 관심사가 아닐 때 진가를 발휘한다. 확정성이 필요하면 이벤트 스케줄러를 별도로 제공해야 하며, 코파티션 데이터는 한 번에 하나의 함수로만 일관되게 처리할 수 있다.

## 9.7 상태 관리

함수는 수명이 짧으므로 대부분의 상태 저장 솔루션은 외부 상태 저장 서비스를 쓴다. FaaS 공급자는 일반적으로 노 로컬 상태 정책을 강제한다. Azure의 Durable Functions처럼 상태 관리를 추상화해 자동으로 외부에 저장하는 프레임워크도 있다.

## 9.8 함수에서 다른 함수 호출

### 9.8.1 이벤트 기반 통신 패턴

한 함수의 출력을 이벤트 스트림에 넣어 다른 함수가 소비하게 한다. 함수는 비FaaS 마이크로서비스와 사실상 같은 방식으로 동작한다. 각 함수가 독립적으로 오프셋을 관리하고, 실패해도 브로커에 이벤트가 남아 있어 손실이 없다.

### 9.8.2 직접 호출 패턴

비동기 직접 호출은 호출한 함수의 성공만 보장될 뿐 호출된 함수의 실패는 감지되지 않아 오프셋이 잘못 커밋될 수 있다. 또 같은 함수를 여러 번 호출하면 인스턴스 간 경합으로 처리 순서가 꼬인다. 순서가 중요하면 동기 호출과 오케스트레이션 패턴을 쓴다. 오케스트레이션 함수는 워커 함수를 차례로 호출하고 결과를 받아 다음 단계에 넘긴다. 이벤트마다 다음 이벤트 처리 전에 모든 워커 호출이 끝나야 오프셋 순서가 보장된다.

## 9.9 종료 및 중단

함수는 작업 완료나 수명 만료(보통 5~10분) 시 종료된다. 종료 전에 컨슈머 클라이언트 연결과 파티션 할당을 어떻게 처리할지 결정해야 한다. 자주 실행되는 함수라면 연결을 유지해 리밸런스 비용을 피하고, 가끔 실행되는 함수라면 연결을 깔끔히 정리해 다른 인스턴스가 파티션을 가져가게 한다.

## 9.10 함수 튜닝

### 9.10.1 넉넉한 리소스 할당

함수별 CPU, 메모리 할당이 너무 많으면 비용, 너무 적으면 처리 시간 증가로 이어진다. 최대 실행 시간은 예상 배치 처리 시간보다 충분히 높게 잡아 간헐적 타임아웃을 예방한다. 외부 상태 저장소 I/O 부하도 함께 고려한다.

### 9.10.2 배치 이벤트 처리 매개변수

배치 처리 실패가 반복되면 최대 실행 시간을 늘리거나 최대 배치 크기를 줄여야 한다. 일부 시스템은 실패 시 배치를 이등분해 자동 재실행하는 기능을 지원한다.

## 9.11 FaaS 솔루션 확장

큐나 순서가 중요하지 않은 이벤트 스트림에서 진가를 발휘한다. 파티셔닝된 스트림에서 순서가 중요하다면 병렬도는 최대 파티션 수까지로 제한된다. 컨슈머가 그룹에 너무 자주 가입/탈퇴하면 리밸런스 교착에 빠질 수 있다. 정적 파티션 할당으로 리밸런스 오버헤드를 제거하고 코파티션 용도로도 쓸 수 있다.

## 9.12 마치며

FaaS는 함수 단위로 마이크로서비스를 구축하는 빠르게 성장하는 클라우드 컴퓨팅 분야다. 트리거는 이벤트 스트림의 새 이벤트, 컨슈머 그룹 랙, 월클럭 시간, 맞춤 로직 등 다양한 신호로 발동된다. 상태 비저장이거나 단순한 상태 저장 비즈니스 문제에 특히 유용하며, 오케스트레이션 패턴으로 함수 호출 순서와 이벤트 순서를 모두 보장할 수 있다.
