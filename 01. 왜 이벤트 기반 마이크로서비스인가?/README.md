# 01. 왜 이벤트 기반 마이크로서비스인가?

조직의 소프트웨어를 만드는 방향은 통신 구조가 결정한다. 기존 아키텍처의 근본 문제는 데이터 통신 구조가 따로 정의되지 않아 구현 통신 구조가 그 역할까지 떠맡고 있다는 점이다. 이벤트 스트림은 빠져 있던 데이터 통신 구조를 정규화된 형태로 채워 넣는다.

## 1.1 이벤트 기반 마이크로서비스란?

서비스는 비즈니스 목표 달성을 위한 작은 단위다. 작다의 기준은 개발 기간 2주 이내 또는 머릿속에 들어오는 크기다. 입력 이벤트 스트림에서 이벤트를 받아 비즈니스 로직을 적용하고 출력 이벤트를 내보낸다. 상태 유무에 따라 stateful, stateless로 분류한다.

결정적 차이: 이벤트는 소비되어도 사라지지 않고 다른 컨슈머가 가져갈 수 있도록 보존된다. 이벤트 기반 패턴 전반의 토대다.

## 1.2 도메인 주도 설계와 경계 콘텍스트

DDD 핵심 용어 네 가지.

- 도메인: 비즈니스가 다루는 문제 공간. 비즈니스 존재 여부와 무관하다.
- 하위 도메인: 도메인의 컴포넌트. 보통 비즈니스 조직 구조를 반영한다.
- 도메인 모델: 도메인을 비즈니스 용도에 맞게 추상화한 것. 솔루션 공간에 속한다.
- 경계 콘텍스트(bounded context): 하위 도메인과 연관된 논리적 경계. 내부는 강한 응집, 경계 간은 느슨한 결합이 원칙이다.

원칙: 경계 콘텍스트는 기술 요건이 아닌 비즈니스 요건 기준으로 정한다. 기술 기준으로 나누면 비즈니스 기능 하나의 책임이 여러 팀에 분산되어 작은 변경이 후폭풍으로 번진다.

## 1.3 통신 구조

조직의 통신은 세 구조로 나뉜다.

- 비즈니스 통신 구조: 팀과 부서 간 통신. 책임 분배 문제다.
- 구현 통신 구조: 코드와 시스템 내부의 데이터와 로직의 통신.
- 데이터 통신 구조: 비즈니스 전반에서 데이터를 주고받는 프로세스.

콘웨이의 법칙: 시스템 구조는 그것을 만든 조직의 통신 구조를 따른다. 데이터 통신 구조가 누락되면 구현 통신 구조가 1인 2역을 떠맡고, 다른 제품에서 도메인 데이터에 접근하기 어려워지며 모놀리스가 비대해진다.

흔한 임시방편(공유 DB, 읽기 전용 레플리카, 배치 파일 덤프)은 모두 점대점 결합과 진실 공급원 다중화라는 부작용을 낳는다.

## 1.4 기존 컴퓨팅의 딜레마

새 비즈니스 요건이 생기면 두 선택지뿐이다.

- 옵션 1, 새 서비스로 분리: 데이터 복제와 동기화 부담, 운영 인프라 이중화.
- 옵션 2, 기존 서비스에 추가: 경계 흐려짐, 응집도 하락, 모놀리스 비대화.

양쪽 모두 막히는 원인은 동일하다. 구현 통신 구조 사이의 데이터 통신 수단이 부실하기 때문이다.

## 1.5 이벤트 기반 통신 구조의 다섯 가지 특성

1. 이벤트가 통신의 근간이다. 공유 데이터는 모두 이벤트 스트림에 발행되며, 이벤트는 데이터이자 비동기 통신 수단이다.
2. 이벤트 스트림은 단일 진실 공급원이다. 팀별 별도 저장소는 백본 기능을 망가뜨린다.
3. 컨슈머가 스스로 모델링과 쿼리를 수행한다. 데이터 접근과 모델링 책임이 프로듀서에서 컨슈머로 이동한다.
4. 조직 전반의 데이터 통신이 정규화된다. 공유 데이터가 구현체 밖으로 노출되어 생산과 소유가 분리된다.
5. 비즈니스 변경이 쉬워진다. 도메인 이벤트가 특정 구현체에 종속되지 않으므로 팀과 프로젝트가 바뀌어도 데이터는 계속 활용된다.

## 1.6 비동기식 이벤트 기반 마이크로서비스의 이점

- 세분성: 경계 콘텍스트에 매핑되어 재작성이 쉽다.
- 확장성: 서비스별 독립 확장.
- 기술 유연성: 서비스별로 적합한 언어와 기술 선택.
- 비즈니스 요건 유연성: 소유권 재조정이 쉽고 변화 대응이 빠르다.
- 느슨한 결합: 도메인 데이터에 결합할 뿐 특정 API에 묶이지 않는다.
- 지속적 전달 지원: 배포와 롤백이 간편하다.
- 우수한 테스트성: 의존성이 적어 모킹과 커버리지 관리가 쉽다.

## 1.7 동기식 마이크로서비스

요청-응답 기반 SOA 방식이다. 넷플릭스, 우버 등도 사용하므로 동기식 자체가 실패는 아니다.

단점:

- 점대점 결합으로 의존이 꼬리를 문다.
- 의존적 확장: 의존하는 모든 서비스의 확장 가능성에 좌우된다.
- 서비스 실패 처리 절차가 복잡하다.
- API 버저닝과 디펜던시 관리 부담.
- 데이터 접근이 구현체에 종속된다.
- 분산 모놀리스화: 점대점 호출이 얽혀 모놀리스 내부 경계를 흉내낸다.
- 통합 테스트가 어렵다.

장점:

- 사용자 인증, A/B 테스트는 요청-응답이 더 적합하다.
- 외부 서드파티는 대부분 동기식 HTTP로 연계된다.
- 작업 추적과 디버깅 가시성이 좋다.
- 웹과 모바일은 본래 요청-응답 기반이다.
- 동기식에 익숙한 개발자가 더 많다.

100% 이벤트 기반 조직은 거의 없다. 하이브리드 아키텍처가 표준이다.

## 1.8 마치며

데이터 통신 구조를 제대로 설계하면 더 작고 목적에 부합한 구현체를 만들 수 있다.
